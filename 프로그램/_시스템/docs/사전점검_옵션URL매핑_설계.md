> **계층**: 프로젝트 설계 문서
> **책임**: 「옵션 조합 생성 및 수정 + 소싱처 URL 매핑」 팝업의 저장 전 검증
> **단일 진실 원천**: 본 문서 (사전점검 한정)
> **상위 의존**: `CLAUDE.md` (데이터 무결성) · `docs/크롤링-가이드.md` (크롤 방식)

## 1. 목표 / 비목표

**목표** — 사장님이 옵션별로 소싱처 URL을 다 넣고 **저장을 누르기 전에**, 한 번의 실행으로
「내가 만든 옵션명」과 「소싱처가 실제로 파는 옵션」이 맞는지 **일괄 대조**해서 보여준다.

**비목표**
- URL 붙여넣을 때마다 자동 크롤 (사장님 결정 — 입력 흐름을 끊음)
- 사전점검용 **간이 크롤 신설** (사장님 지시 — 정규 크롤과 100% 동일해야 함)
- 매핑 자동 확정 (제안만, 확정은 사람이)

## 2. 배경 실측 (2026-08-02, 라이브 U20260802-000177)

| 항목 | 값 |
|---|---|
| 등록 URL | 무신사 4개, 전부 `단품`, 라벨 `무신사_{색}` |
| 옵션 | 42개 (색 7종 × 사이즈 6) — 매트릭스는 4×6=24칸만 표시 |
| URL 붙은 옵션 | **24 / 42** (나머지 18개는 `색상1~3` 옛 축 값 잔재) |
| 저장 시 검증 | **없음** — URL 문자열이 비었는지만 확인 |

→ 오타 URL·소싱처에 없는 색·안 파는 사이즈를 칠해도 저장은 100% 성공한다.
→ 결과는 크롤을 돌려 매트릭스를 봐야 드러난다. 이 지연을 없애는 것이 본 설계.

## 3. 설계 원칙 3가지

**원칙 1 — 크롤 코드는 한 줄도 새로 쓰지 않는다.**
소싱처별 정규 경로를 그대로 호출한다. 가격·재고 산출식, 로그인 프로필, 429 페이싱,
혜택 차감까지 평소 크롤과 동일해야 한다. (사장님 지시)

**원칙 2 — 점검 결과와 나중 매트릭스 값이 어긋나면 안 된다.**
따라서 판정에 쓰는 매칭기는 매트릭스가 쓰는 것과 **같은 하나**여야 한다.
현재 매칭기가 5개로 갈라져 있으므로(§12), **이미 있는 별칭 엔진**
(`lemouton/mapping/matcher.py`)을 **단일 원천으로 승격**한다.
※ 초안의 「`_match_option_so` 를 공용 모듈로 분리」는 **폐기**. 그 함수는 사전을 안 보고
모델 축도 없어, 공용으로 올리면 약점이 전체로 퍼진다. (2026-08-02 사장님 승인)

**원칙 3 — 점검은 「내 매핑」을 저장하지 않는다.**
소싱처 크롤 결과(SourceProduct/SourceOption)는 평소 크롤과 똑같이 저장된다.
옵션 목록·URL 카드·매핑은 [저장] 버튼을 눌러야만 저장된다.

## 4. 소싱처별 정규 크롤 경로 (그대로 사용)

| 소싱처 | 정규 경로 | 사전점검이 부를 것 |
|---|---|---|
| 무신사 | 크롬 확장 `fetchMusinsaAdapter` | 확장 `MoumExt.crawl` |
| 롯데온 | 크롬 확장 (창 경로) | 확장 `MoumExt.crawl` |
| 르무통·SSF·스스 | 확장 fast-lane / 서버 크롤러 | 확장 우선, 없으면 서버 |
| SSG·롯데아이몰 | 확장 same-origin fetch | 확장 `MoumExt.crawl` |
| H몰 | 확장 `fetchHmallAdapter` | 확장 `MoumExt.crawl` |
| 크롤러 없는 곳 | — | **⚫ 점검 불가**로 표시 (성공으로 위장 금지) |

확장은 URL 목록을 직접 받으므로 **DB 저장 전에도 크롤 가능**하다
(`ext_bridge.js` `MoumExt.crawl({model_code, sources:[{source_key,url,url_type}]})`).

서버 경로는 현재 DB 행(`OptionSourceUrl` / `BundleSourceUrl`)을 요구해 저장 전엔 못 쓴다.
→ **입구만 하나 신설**(§5-B). 내부는 기존 `fetch_one_source` 그대로 호출한다.

## 5. 신설 API 2개

### A. `POST /api/bundles/<code>/precheck-mapping`
점검의 본체. **크롤 결과를 받아** 우리 옵션과 대조한 판정표를 돌려준다.

```
요청  {
  options: [{canonical_sku, axis_values:[색,사이즈], mapped_url_ids:[...] }, ...],  # 화면 상태 (미저장)
  urls:    [{tmp_id, source_key, url, url_type, label, option_keys:[...]}, ...],    # 화면 상태 (미저장)
  crawled: [{tmp_id, status, options:[{color,size,price,stock}], error}, ...]        # 확장/서버 크롤 결과
}
응답  { ok, rows:[{sku, color, size, url_tmp_id, verdict, source_price, source_stock, reason}],
        summary:{ok, missing_at_source, unmapped, uncheckable, crawl_failed},
        type_warnings:[{tmp_id, msg}] }
```

판정은 §6 규칙을 따르며, `_match_option_so` 와 **동일 함수**를 쓴다.
**DB 쓰기 없음.**

### B. `POST /api/sources/precheck-crawl` (서버 담당 소싱처용)
확장이 담당하지 않는 소싱처를 저장 전에 크롤하기 위한 입구.

```
요청  { items: [{source_key, url, url_type}] }
응답  { results: [{url, status, options:[{color_text,size_text,price,stock}], error}] }
```

내부 = `build_crawlers()` + `upsert_source_product` + `fetch_one_source`.
**기존 정규 크롤 함수 그대로.** 새 파서·새 가격식 금지.

## 6. 판정 규칙 (5상태)

행 단위 = **(우리 옵션 1개 × 그 옵션에 매핑된 URL 1개)**.

| 상태 | 조건 | 화면 | 제안 |
|---|---|---|---|
| ✅ **맞음** | 매핑했고, 소싱처 옵션에서 색+사이즈 매칭 성공 | 가격·재고 표시 | — |
| 🔴 **소싱처에 없음** | 매핑했는데, 소싱처가 그 색·사이즈를 안 팜 | 빨강 | 매핑 해제 |
| 🟡 **안 칠함** | 소싱처엔 있는데 그 옵션에 URL을 안 붙임 | 노랑 | 매핑 추가 |
| ⚫ **점검 불가** | 크롤러 없음 / 확장 꺼짐 / 로그인 필요 | 회색 | 확장 켜기 안내 |
| ⚠️ **대조 불가** | 우리 사이즈에 숫자가 없음(S·M·L·FREE) | 주황 | 별도 안내 |

⚠️ 는 현재 매칭기가 **사이즈에서 숫자만 뽑아 비교**하기 때문이다
(`_stk_digits`, api_pricing.py:108). 숫자 사이즈가 아니면 매칭이 구조적으로 불가능하므로
「소싱처에 없음(🔴)」으로 뭉뚱그리지 않고 **원인을 분리해서 표시**한다.

**유형 경고** (같은 표에서 함께 표시)
- `단품`인데 소싱처 색이 2종 이상 → 「색상모음전 아닌가요?」
- `색상모음전`인데 색이 1종 → 「단품 아닌가요?」
- `모델모음전` → 현재 **미지원** 경고 (소싱처 옵션 저장 열쇠가 `(URL,색,사이즈)`뿐이라
  모델이 달라도 색·사이즈가 같으면 덮어써짐 — `service.py:117`)

## 7. 화면

**위치** — 팝업 하단, `[취소]` 와 `[옵션 N개 + URL 저장]` 사이에 `[일괄 사전점검]`.

**흐름**
1. 누르면 화면의 URL 카드를 **저장 안 된 것까지 전부** 모은다
2. 소싱처별 정규 경로로 크롤 (진행 표시 「무신사 2/4」)
3. 결과표를 팝업 안에 편다 — 요약 한 줄 + 상태별 접기

```
점검 결과   ✅ 24   🔴 0   🟡 0   ⚫ 0   ⚠️ 0
└ ✅ 맞음 24 ▸
└ 🔴 소싱처에 없음 0
```

**저장 게이트** — 🔴 가 남아 있으면 저장 시 확인창:
「베이지 6칸은 무신사에 없습니다. 그래도 저장할까요?」 → **막지 않고 경고만**
(신상품이 아직 소싱처에 안 올라온 경우가 있음 — 사장님 결정)

## 9. 검증 방법 (이 설계가 됐는지 아는 법)

1. **무변화 증명** — 1단계 후 라이브 상품의 매트릭스 값 전수 비교 → 변경 0건
2. **정답 케이스** — U20260802-000177 점검 → `✅ 24 · 나머지 0` (실측 기대값)
3. **오답 케이스** — 「베이지」를 무신사 다크네이비 URL에 일부러 매핑 → 🔴 6건 잡힘
4. **끊김 케이스** — 확장 끄고 실행 → 전부 ⚫, **✅ 로 위장하지 않음**
5. **동일성 증명** — 점검이 보여준 가격 = 저장·크롤 후 매트릭스 가격 (전 옵션 일치)

5번이 원칙 1·2의 실제 합격 기준이다.

## 12. 별칭 엔진 승격 (2026-08-02 추가 — 사장님 승인)

### A. 지금 매칭기가 5개다

| # | 매칭기 | 사전 봄? | 무엇을 결정 | 상태 |
|---|---|---|---|---|
| 1 | `lemouton/mapping/matcher.py` — 차원·별칭·학습·점수 | ✅ 별칭표 | 가장 강력 | **부르는 곳 0곳** |
| 2 | `lemouton/sources/option_matcher.py` | ✅ ColorDict | 마켓 옵션ID | 소싱처 미연결 |
| 3 | `lemouton/sources/bundle_url_crawl.py:_build_matcher` | ✅ ColorDict | 크롤 저장 링크 | 동작 |
| 4 | `webapp/routes/api_pricing.py:_match_option_so` | ❌ **안 봄** | **매트릭스 화면 값** | 동작 |
| 5 | `webapp/routes/api.py:_build_color_mapping` | ✅ ColorDict | 옛 진단 | 새 URL 미연결 |

**사장님이 보는 화면은 5개 중 유일하게 사전을 안 보는 4번이 결정한다.**
라이브 실증 — `블랙 = ["블랙","Black","BK","검정"]` 이 등록돼 있는데도
소싱처가 `black` 이면 매트릭스는 매칭 실패한다.

### B. 라이브 상태 (origin/main 기준)

- `lemouton/mapping/matcher.py` · `models.py` → **라이브에 있음**
- `webapp/routes/mapping.py`(화면) → **main 에 없음** → `/mapping` 라이브 404
- 본체 `match_options_batch` → **부르는 곳 0곳**. 쓰이는 건 `normalize` 하나뿐
- 즉 **엔진은 살아 있고 배선만 끊긴 상태.** 새로 만드는 게 아니라 잇는 일이다.

### C. 색상 vs 모델 — 위험도가 다르다

`alias_mappings` 에는 **소싱처·브랜드 구분(scope)이 없다. 전역이다.**

| 차원 | 전역 별칭이 맞나 | 판단 |
|---|---|---|
| **색상** | ✅ `black` 은 어디서나 블랙 | **가장 잘 맞음 — 1순위 전환** |
| 사이즈 | ✅ 대체로 안전 | 색상과 함께 |
| **모델** | ⚠️ 「클래식」이 브랜드마다 존재 | **scope 정한 뒤 붙임 (7단계)** |

모델의 추가 위험 — UNIQUE 가 `(캐노니컬, 별칭)` 이라 **같은 별칭이 두 캐노니컬에
각각 등록될 수 있다.** 회피책: 모델 별칭은 「브랜드+모델」 형태로 등록.
근본책: 차원에 scope 컬럼 추가 (별건).

### D. 이관 규칙 (조용한 후퇴 방지)

1. ColorDict → 색상 차원 캐노니컬 + 별칭으로 **복사** (이관 아님)
2. **ColorDict 테이블은 지우지 않는다.** 읽기만 끊는다 — 되돌릴 수 있게
3. 전환 전후 라이브 전 옵션 **전수 대조 → 변경 0건** 확인 후에만 다음 단계
4. 참조처 5곳(§12-A)을 **한 번에** 바꾼다. 하나만 남기면 분열이 더 심해짐
5. 별칭표 조회는 요청당 1회 캐시 (매트릭스는 수백 행 렌더)

## 13. 모델 차원 사용 결정에 따른 추가 (결함 ⑧)

사장님이 모델 차원을 쓰기로 하셨으므로, 매칭만으로는 부족하다.

**문제** — 소싱처 옵션 저장 열쇠가 `(URL, 색, 사이즈)` 뿐이다
(`lemouton/sources/service.py:117`). 모델모음전 URL 하나에 모델 A·B 가 있고
둘 다 「블랙 250」이면 **나중 것이 앞의 것을 덮어쓴다. 경고 없음.**

**대응**
1. `SourceOption` 에 `model_text` 추가 → 열쇠를 `(URL, 모델, 색, 사이즈)` 로 확장
2. 크롤러가 옵션 단위 모델명을 담도록 (현재는 상품 단위 `product_name_raw` 만)
3. 기존 행은 `model_text = NULL` 로 두고 단품·색상모음전은 동작 불변
4. 마이그레이션 후 **모델모음전 URL 1개로 실측** — 옵션 수가 모델 수만큼 늘어나는지

**순서** — §8 의 7단계. 1~6단계(색상·사전점검)가 끝나고 무변화가 증명된 뒤에 착수.

### B. 축 맞춤이 곧 사전 한 줄

`검정 → BLACK` 을 고르는 행위 = 별칭 사전에 한 줄 쌓기.
그래서 같은 소싱처의 **다음 상품에서는 물어보지 않는다.** 조합 매핑은 상품마다 처음부터 다시라
이 차이가 본 설계의 실질 이득이다.

| 고르는 횟수 | 조합마다 | 축마다(확정) |
|---|---:|---:|
| 6색 × 10사이즈 | 60 | **16** |
| 내장 사전 자동 처리 후 | 60 | **2** |
| 같은 소싱처 다음 상품 | 60 | **0** |

### C. 3단 계단 (매칭 순서 — 이 순서 고정)

1. **정규화** — 띄어쓰기·대소문자·`-_.` 제거. `다크 네이비` = `다크네이비` (사전 없이 통과)
2. **내장 사전** — `shared/sku_format.py` COLOR_ALIASES 21종 · SIZE_ALIASES 16종
   (`블랙=black·bk·검정`, `250=7us·8us·250mm`, `FREE=onesize·균일`)
3. **축 매핑(DB)** — 사장님이 드롭다운으로 고른 것. 소싱처 scope. 여기서만 학습이 쌓인다

**모델 축은 1·3단만 있다** (모델 내장 사전 없음). 별칭에 브랜드 구분이 없으므로
모델 값은 「브랜드+모델」 표기로 등록한다 (§12-C).

### D. 실측 — 새 방식과 지금 방식이 정반대로 틀린다

| 소싱처 표기 | 우리 표기 | 새 방식 | 지금 매트릭스 |
|---|---|:---:|:---:|
| `다크 네이비` | 다크네이비 | 붙음 | 붙음 |
| `블랙` | 검정 | 붙음 | **놓침** |
| `BLACK` / `Dark Navy` | 블랙 / 다크네이비 | 붙음 | **놓침** |
| `블랙&화이트` | 블랙 | 안 붙임 | **잘못 붙음** |
| `네이비` | 다크네이비 | 안 붙임 | **잘못 붙음** |
| `오프화이트` | 화이트 | 안 붙임 | **잘못 붙음** |
| `블랙 (블랙아웃솔)` | 블랙 | 안 붙임 | **잘못 붙음** |

지금은 **애매하면 붙여버린다**(부분일치). 새 방식은 **확실할 때만 붙이고** 나머지는 사람에게 보낸다.

> ⚠️ **그래서 전환 시 「변경 0건」이 나오지 않는다.** 그동안 잘못 붙어 있던 값이 떨어져 나간다.
> 검증 기준은 「변경 0건」이 아니라 **「떨어져 나간 목록을 뽑아 사장님이 확인」** 이다.
> 이 목록이 곧 그동안 잘못된 가격을 보고 있던 옵션들이다.

## 16. ★구현 순서 (확정)

| 단계 | 무엇을 | 끝났다고 말할 수 있는 근거 |
|---|---|---|
| **0** | 유령 옵션 정리 (`색상1~3` 18개) | 라이브 옵션 수가 매트릭스 칸 수와 일치 |
| **1** | 축 매핑 저장소 — `(소싱처, 축이름, 우리값) → 소싱처값` | 표 생성 + 되돌리기 경로 확인 |
| **2** | 매칭 3단 계단 함수 1개로 통합 (§15-C) | 단위 테스트 — §15-D 표의 9개 사례가 표대로 나옴 |
| **3** | 매트릭스가 그 함수를 쓰게 교체 | **떨어져 나간 목록 뽑아 사장님 확인** (변경 0건 아님) |
| **4** | 확장이 주는 `options[]` 살리기 (`ext_bridge.js`) | 콘솔에 색·사이즈 목록이 찍힘 |
| **5** | 저장 전 불러오기 입구 — 확장 경로 + `POST /api/sources/precheck-crawl` | 저장 안 된 URL 4개로 옵션 30개 회수 |
| **6** | 탭 신설 + **1층 축 목록·드롭다운** | 라이브 상품에서 축 16줄 · 자동 14 · 확인 2 |
| **7** | **2층 조합 격자**(보기 전용) + 저장 게이트 | 「축 미정」 남기고 저장 시 경고가 뜸 |
| **8** | 모델 축 — 저장 열쇠에 모델 추가(§13) + 크롤러가 옵션 단위 모델 회수 | 모델모음전 URL 1개에서 모델별 옵션이 안 겹침 |

**순서 이유**
- 0~3 은 **화면이 없다.** 값이 맞아진 뒤에 화면을 얹어야, 화면이 틀렸는지 값이 틀렸는지 구분된다.
- 3 이 가장 위험하다 — 잘못 붙어 있던 값이 사라지므로 **사장님 확인 없이 넘어가지 않는다.**
- 4~5 는 **불러오기**. 6~7 이 화면. 8(모델)은 저장 구조를 건드리므로 맨 뒤.

### 미결 (착수 전 확정 필요)

## 17. 이 설계가 건드리지 않는 것

- 매트릭스 표시 로직 (1단계는 함수 위치만 이동, 동작 동일)
- 크롤러·파서·가격 계산식 (한 줄도 안 고침)
- 옵션 생성/삭제 (`prune`) 동작
- 유령 옵션 18개 — **별건**. 본 설계에선 ⚠️/제외로만 다룸

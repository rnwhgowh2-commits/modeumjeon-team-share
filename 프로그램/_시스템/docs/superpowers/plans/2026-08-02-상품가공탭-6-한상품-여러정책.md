# 상품 가공 6단계 — 「한 상품에 여러 정책」 + 그룹핑

> 노션 「무재고 모음전 솔루션 개발현황」 §상품 가공 하위탭 ② 의 마지막 두 항목.
> 사장님 확정 (2026-08-02):
> - **「같은 마켓에 여러 벌 올리기」** — 한 상품을 정책마다 다르게 가공해 같은 마켓에 각각 등록
> - **재고는 「데이터 연동」** — 벌마다 몫을 나누지 않는다. 같은 재고를 보고, 팔리면 같이 준다
> - **그룹핑도 이번에 같이**

---

## 🔍 조사로 뒤집힌 전제 (이게 계획의 전부를 바꿨다)

처음엔 「제일 큰 공사 — 열쇠(PK) 수술 필요」로 봤다. **틀렸다.**

**① 「벌」은 이미 있다. 이름이 「구성(ProductSet)」이다.**

```
Model(상품)  └ ProductSet(구성=벌)  ← model_code 가 UNIQUE 가 아니다 → 여러 개 가능
                └ SetChannel(마켓×계정)  ← market_product_id 를 각자 들고 있다
                    └ SetChannelOption(canonical_sku ↔ market_option_id)
```

**② 재고 연동도 이미 된다.** `reconcile.market_targets_for(sku)` 는 그 SKU 가 걸린
**모든** 구성·마켓·계정을 돌려준다. 구성이 둘이면 둘 다에 같은 재고가 나간다 —
사장님이 고르신 「데이터 연동」이 곧 지금 동작이다.

**③ 라이브 실측 (2026-08-02)** — 모음전 90개 중 **89개는 구성 0개**.
유일한 실상품 `르무통_메이트` 만 **구성 2개**. 즉 「한 상품에 여러 벌」은 이미 라이브에서 돌고 있다.

**④ 돈이 나가는 길의 기준선은 `PriceSnapshot`이다** (`plan_uploads` → `last_confirmed_snapshot`).
`MarketRegistration`(PK 가 sku+market 이라 수술이 필요한 그 표)은 **드라이런 미리보기에서만** 쓴다.
`PriceSnapshot` 은 id 가 PK 라 **칸만 더하면 된다**.

→ 결론: **PK 수술 0건.** 새 표 1개 + 칸 1개면 된다.

---

## 🔴 그래서 진짜 빠진 것은 딱 하나

정책이 **상품(model_code)** 에 붙는다 — `bundle_policy_links.model_code` 가 PK 라 1:1.
벌(구성)마다 다른 정책을 줄 자리가 없다. **정책을 구성에 붙이면 끝난다.**

가격 되받기 사슬 (위가 이긴다):

```
구성 정책  →  상품 정책  →  가격 템플릿  →  (없으면) 마켓 기본
```

🔴 되받기가 핵심이다. 구성에 정책을 안 붙인 곳은 **지금 값 그대로** 나가야 한다.
5단계에서 이미 증명한 원리와 같다(`as_template` 의 `_policy_or_fallback`).

## 하지 않는 것

- **재고 몫 나누기** — 사장님이 「데이터 연동」으로 확정. 몫 배분은 안 만든다.
- **`MarketRegistration` PK 수술** — 드라이런 미리보기에서만 쓰므로 이번 범위 밖.
  (구성이 둘일 때 미리보기 기준선이 대략치가 될 수 있음 — 화면에 그대로 적는다)
- **「가격 정책」 탭 삭제** — 사장님이 "이번엔 건드리지 않는다".

# samba-wave는 모음전과 완전히 독립적으로 운영하고, 판매처 계정만 공유한다

대량등록 탭을 samba-wave(다른 사업에서 쓰던 별도 플랫폼, FastAPI+Next.js)로 대체하기로 하면서,
샘바웨이브 로직을 모음전(Flask)에 이식하는 방법과 완전히 독립된 시스템으로 나란히 운영하는 방법을
검토했다. 스택이 근본적으로 다르고(Flask/Jinja vs FastAPI+Next.js+멀티테넌트), 배포 대상도 다르며
(Fly.io+Supabase vs Cloud Run 계열), 이식은 두 팀이 감당하기엔 큰 작업이라 판단해 **완전 독립 운영**을
택했다. 단, 판매처(쿠팡·11번가·옥션 등) 로그인/API 자격증명만은 두 시스템이 실제로 같은 값을 써야
하므로 예외로 공유하며, 그 형식은 samba-wave 의 `samba_market_account` 스키마를 표준으로 삼고
모음전이 따라간다(반대 방향 아님).

대량등록과 samba-wave collector 는 기능이 상당 부분 겹친다는 것을 알고 있지만, 지금 당장 합치지
않고 둘 다 독립적으로 운영하다가 이후 "효율적인 방법을 비교"해서 통합 여부를 다시 판단하기로 했다 —
지금 성급하게 합치면 어느 쪽 방식이 더 나은지 검증할 기회 자체가 사라진다.

## Considered Options

- **로직 이식** (Claude 최초 추천) — samba-wave 의 collector 로직만 Flask 로 새로 짜서 이식. 스택 하나로 유지되지만, 이식 자체가 큰 작업이고 samba-wave 쪽 개선을 계속 다시 이식해야 함.
- **전체 스택 전환의 첫걸음** — 모음전 전체를 FastAPI+Next.js 로 옮기는 계획의 일부로 편입. 지금 필요한 것보다 훨씬 큰 범위라 기각.
- **완전 독립 + 계정만 공유** (채택) — 두 시스템을 따로 배포·운영. 지금은 중복이 있어도 감수하고, 나중에 실측 비교 후 통합 판단.

## Consequences

- 모음전은 판매처 계정을 더 이상 자체 형식(플랫폼별 파일 캐시)으로 새로 늘리지 않고 samba-wave 스키마를 따라가야 한다 — 기존 `shared/platforms/*/token_store.py` 류는 이 표준에 맞춰 정리 대상이 된다.
- 두 시스템 간 판매처 계정 공유의 정확한 방식(API 호출 vs 같은 DB 직접 접근)은 이 결정에서 아직 안 정해짐 — STEP 2b 에서 확정한다.
- 대량등록과 samba-wave collector 의 중복 기능은 당분간 그대로 둔다 — 성급한 통합 방지가 의도된 선택이다.

## 4. ⚔️ 세션 충돌 → 해소 결론 (제가 코드로 심판함)

### 4-1. 999 재고 → **축 분리, 둘 다 맞음**
- 재고 세션: "999 = 재고있음(수량미상), 정상" ← **소싱처 매트릭스** 표시 기준
- 판매처 심화 세션: "999를 카드 재고 총합에서 '미상'으로 제외" ← **판매처 카드 총합** 기준
- **결론**: 층이 다름. 소싱처 매트릭스는 999를 '재고있음'으로 유지, 판매처 카드 총합은 센티넬 제외. 모순 아님. 단 "파싱 실패로 생긴 999"는 "정상 수량미상 999"와 구분(SSG 필드부재 사례). [[feedback_stock_999_not_a_bug]]

### 4-2. 95,000원 → **경로 분리, 둘 다 맞음**
- 모음전 상세 감사: "소싱 카드의 95,000 가짜 판매가 = 폴백, **제거함**"(origin/main)
- 판매처 세션: "사입 카드의 95,000 = purchase_resolved_avg(정상 template 매입가), **유지**"
- **결론**: 같은 숫자, 다른 경로(소싱 카드 vs 사입 카드). 한쪽만 보고 "95000 폴백 제거/유지" 단정 금지.

### 4-3. 롯데온 base 정의 → **해소 (이중차감 아닐 가능성 높음)**
- PR#80(혜택 세션): 판매가 119,910을 base로 롯데오너스 1% 차감
- 표면가 세션 확인: **롯데온 표면노출가(판매가) = 119,910** (7색 라이브 일치). 롯데오너스는 그 위에 붙는 혜택.
- **결론**: 표면가 119,910을 base로 삼고 롯데오너스를 차감하는 PR#80 모델은 **이중차감 아님(정상).** 단 119,910이 이미 포함한 화면 할인(19% 등)과 롯데오너스가 겹치지 않는지만 **PR#80 머지 직전 최종 확인.**

### R1. 서버 크롤 제거 (1-2) — 가장 파괴적 🔴
- **위험**: 순서 틀리면 크롤이 통째로 멈춘다. 워커큐는 구현됐으나 (a)스케줄러 미배선 (b)UI 버튼 3종(홈 지금바로실행·번들 ▶실행·↻재시도, api.py:1825·2855·3103·3210)이 아직 서버 크롤 호출 (c)로컬 PC 워커가 실제 가동돼야 큐 소비. 지금 서버 크롤은 르무통·SSF는 성공 중 → 성급히 떼면 그것마저 중단.
- **대책(순서 엄수)**: ① 로컬 워커 실가동 확인(엔드투엔드 1건 크롤→저장) → ② scheduled_dispatch 스케줄러 배선 → ③ UI 버튼 3종을 enqueue_crawl로 재배선 → ④ 그 다음에야 서버 직접 크롤 제거 → ⑤ 전환 중 큐 미소비 시 **경고 표면화**(조용히 멈추지 않게).

### R2. 조용한 실패를 '시끄럽게' 만들 때 (1-3: #11·#12·#14·위젯) — 역설적 위험 🟡
- **위험**: 지금 catch로 삼켜 '성공'처럼 굴러가던 흐름이, 실패를 드러내는 순간 **대량 에러·빨간불**로 표출 → 사용자 놀람·흐름 차단. 부분 실패 많으면 대시보드가 온통 경고.
- **대책**: 하드 실패(throw)로 바꾸지 말고 **'부분 성공 + 실패 건수 표면화'**. 수집은 계속하되 실패를 카운트·로그·배지로. 위젯(#6)은 '저장 N건 실패'를 성공 카운트와 **분리 표기 + 재시도 버튼**. 한 번에 다 켜지 말고 항목별 단계 배포·라이브 관찰.

### R3. 999 센티넬 손댈 때 (데이터#5 + 판매처#10) — 층 교차 회귀 🟡
- **위험**: 999 처리는 **소싱처 매트릭스(999=재고있음 정상)** 와 **판매처 카드(999=미상 제외)** 가 공유 코드(_resolve_stock 등)를 볼 수 있음. 한 층 고치다 다른 층 회귀.
- **대책**: **표시 층에서만 분기**, 저장·정규화 원본은 안 건드림. 전송(#10)은 센티넬을 '수량 미상'으로 치환하되 실재고 0/양수와 구분, 전송 ON 전 dry-run으로 999 push 0 확인. all-999 과잉진단 금지 [[feedback_stock_999_not_a_bug]].

### R4. 95000 / 폴백가 손댈 때 — 재실수 위험 🟡

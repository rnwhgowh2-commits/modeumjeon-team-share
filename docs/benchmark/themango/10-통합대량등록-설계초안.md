## 2. 🔴 설계 전 정정 2건 — 실측이 앞선 진단을 뒤집었다

### 정정 ① 「정책 시스템이 두 벌」 — **항목 정의는 이미 한 벌이다**

§08-6 과 §README-⑤ 는 우리 진짜 숙제를 *"정책 시스템이 두 벌 → 배울 진짜는 두 벌 합치기"* 라고 적었다.
**절반만 맞다.** 실코드는 이렇다:

```python
# lemouton/policy/fields.py:18   ← 모음전 정책
from lemouton.registration.process_rule_schema import all_schemas
...
# :82~83
def base_items():
    """대량등록 가공 규칙 13항목 — 정의를 그대로 가져온다(베끼지 않는다)."""
    return [dict(s, only=None) for s in all_schemas()]
```

**모음전 정책 화면은 대량등록의 13항목 스키마를 직접 불러다 쓴다.** 베낀 게 아니라 그대로 쓴다.
`required.py` 의 마켓별 필수 표시도 같은 13개 키(`name`·`category`·`price`·`options`·`images`·`detail`·`shipping`·`notice`·`brand`·`origin`·`kc`·`tags`·`banned_words`)를 쓴다.

**저장 그릇의 모양도 사실상 같다:**

| | 모음전 | 대량등록 |
|---|---|---|
| 헤더 | `MarketPolicy`(name·brand·enabled_markets·is_default) | `ProcessPolicy`(name·description) |
| **값** | `MarketPolicyValue`(**policy_id · market · field_key · value** · `from_common_at`) | `ProcessRule`(**policy_id · market · item_key · config**) |
| 마켓 축 | `market` 칸 | `market=''` 공통 / `market='coupang'` 덮어씀 |

→ **같은 표를 이름만 다르게 두 벌 들고 있는 것.**
게다가 대량등록의 `ProcessRule` 은 이미 **「공통 < 마켓별」 2단 상속**을 한다.

> **그래서 진짜 숙제는 「두 벌 합치기」가 아니라 「붙이는 층 하나로 모으기」다.**
> 항목 어휘도 값 그릇 모양도 이미 같다. **다른 건 「무엇에 붙느냐」 뿐이다.**
> 합치는 비용이 겁냈던 것보다 훨씬 작다.

### 정정 ② 롯데온 — 「구분 컬럼이 없다」가 문제가 아니었다

§09 참조. 롯데온 등록은 카테고리를 **우리가 고르지 않는다.**
`compile_more.py:148 compile_lotteon` 이 「본보기 기존 상품번호(`LO…`)」를 받아 **그 상품의 카테고리·고시·배송·출하지를 통째로 상속**한다.
→ 컬럼을 채워도 그 값이 등록에 안 실린다. **막이개가 먼저다.**

## 3. 뼈대 — 새 개체 **3개** + 기존 확장 **2개**

> 새로 만드는 표는 **3개뿐**이다. 나머지는 이미 있는 것을 넓힌다.
> 🔴 재구현 금지 명부는 §7.

### 3-1. 🆕 **검색필터** (`SearchFilter`) — 대량등록의 중심축

**푸는 문제** — 「무신사에 나이키 검색한 결과 전부」라는 **수집 행위를 영구 개체로** 만든다.
지금 우리는 URL 1개 → 초안 1개(`draft_from_url.py`)뿐이라 **리스팅 URL → 다건이 통째로 없다.**

| 칸 | 뜻 |
|---|---|
| `name` | 자동 생성 (`무신사_나이키_001`). 사람이 고칠 수 있음 |
| `source_key` · `listing_url` | 어느 소싱처의 어느 검색 결과인가 |
| `max_items` | **저장상품수 상한** — 몇 개까지만 담을지 |
| `page_from` · `page_to` | **저장 페이지 범위** |
| `banned_template_id` | 수집 시점 **금지어 템플릿** |
| `option_exclude_words` | **옵션 수집 제외** (이 말이 든 옵션은 안 담음) |
| `apply_policy_id` | **수집 즉시 정책 적용** |
| `last_run_at` · `last_new_count` | 마지막 실행·새로 들어온 수 |
| `deleted_at` | 🔴 **필터를 지워도 상품은 안 지운다** (더망고 함정 §08-4) |

**상품과의 연결** — `ProductDraft.search_filter_id` 칸 하나 추가(비어 있어도 됨).
수기 등록 상품은 비어 있고, 검색필터로 들어온 상품만 채워진다.

**🔵 우리 강점과 접합** — `CrawlWeightRule.scope_type` 이 이미 `source｜brand｜model｜url` **4단**을 지원한다.
**여기에 `search_filter` 를 5번째로 얹으면** 가중 랩·계수 엔진이 **그대로 재사용된다.**
→ **「신규상품수집」은 새 기능이 아니라 「검색필터를 랩에 태우는 것」이다.**

### 🔴 실행 배선 정정 (2026-08-06 구현 중 실측)

이 문서는 앞서 *"실행은 `CrawlJob`(서버가 등록 → 로컬 워커가 선점·실행)을 그대로 탄다"*고 적었다.
**틀렸다. `CrawlJob` 큐는 소비하는 워커가 저장소에 없다.**
근거 — `webapp/routes/sourcing_guide.py:975~977` 원문:
*"종전 「검증」 버튼은 crawl_queue 에 잡을 넣었지만 그 큐를 소비하는 워커가 저장소에 없어 영원히 '대기'였다."*

**살아 있는 경로는 하나뿐** — 확장이 `/api/crawl/due-bundles` 를 1분 알람으로 폴링하고
(`extension/moum-crawler/background.js:2363`) 결과를 `/api/sources/crawl-result` 로 민다.
→ 검색필터도 **그 옆에** 붙였다: `GET /api/crawl/due-listings` · `POST /api/crawl/listing-result`.
🔴 **앞으로 크롤 성격의 신기능은 전부 이 자리에 붙여야 한다.** `CrawlJob` 은 쓰지 않는다.

### 🟢 찾은 주소 → 상품 (2026-08-07 구현 완료)

**빠진 고리는 한 칸뿐이었다** — 나머지는 이미 있었다.

```
찾은 주소(SearchFilterItem)
    │ ① 크롤 대상 등록  ← 이것만 새로 만듦 (`upsert_source_product` 재사용)
    ▼
SourceProduct ──(확장이 가중 랩으로 크롤 · 이미 있음)──▶ 가격·재고·옵션·이미지
    │ ② 초안 만들기 (`build_draft_from_source` · 이미 있음)
    ▼
ProductDraft (`search_filter_id` 새김 → 성적표의 연결고리)
```

- 통로 = `POST /bulk/api/search-filters/<id>/build` · 화면 = 「상품 만들기」 단추 한 개
- 한 단추가 **두 걸음을 겸한다** — 갈 수 있는 데까지 가고, 크롤이 돈 뒤 또 누르면 그만큼 는다
- 🔴 **자동으로 크롤 대기에 안 넣는다** — 검색 한 번에 수백~수천이 들어오는데 자동이면
  사장님 모르게 크롤 부하가 몇 배가 된다(수집 시점 필터가 아직 안 먹어 더 그렇다)
- 🔴 **「크롤됨」의 증거는 `last_status=='ok'` 하나뿐** — 행이 있다고 크롤된 게 아니다
  (방금 우리가 만든 빈 행일 수 있고, 그걸로 초안을 만들면 텅 빈 상품이 조용히 생긴다)
- 🔴 **판매가는 0으로 둔다** — 크롤은 매입가만 안다. 지어내지 않고 preflight 가 막게 한다
- 필터 「지우기」는 무엇이 남는지 먼저 말한다(만든 상품·찾은 주소 기록 둘 다 남음)

### 3-2. 🆕 **정책 붙임표** (`PolicyBinding`) — 두 벌 합치기의 유일한 신설

**푸는 문제** — 지금은 정책을 붙이는 표가 **대상마다 따로**다.
`BundlePolicyLink`(상품) · `SetPolicyLink`(구성) · `ProcessPolicySource`(소싱처×브랜드).
여기에 검색필터·카테고리·개별상품이 더 붙으면 **표가 6개**가 된다.

**하나로 모은다:**

| 칸 | 뜻 |
|---|---|
| `scope_type` | 무엇에 붙었나 — `default`·`category`·`search_filter`·`source_brand`·`model`·`set`·`draft` |
| `scope_key` | 그 대상의 열쇠 (`model_code`, `filter_id`, `source_key|brand` …) |
| `policy_id` | 어느 정책 |
| `priority` | 층 번호 (아래 §4) |

기존 3개 표는 이 표로 **옮기고 없앤다**(같은 내용이므로 데이터 이동만).

**✅ 「한 구성은 한 정책에만」(2026-07-19 확정) — 사장님 재확인 완료(2026-08-06, a안).**
같은 층 안에서는 여전히 **유일**(`UNIQUE(scope_type, scope_key)`)이다.
**다른 층끼리만** 겹칠 수 있고, 그때는 **위층이 이긴다.**
→ 확정을 지키면서 상속을 얻는다. `PolicyConflict` 는 **같은 층 검사로 남는다.**

## 4. 정책 상속 — 층을 세운다

더망고는 3단(개별 > 검색필터 > 카테고리)이다. 우리는 두 모드가 있으므로 **모드별 사슬**로 둔다.
같은 표(`PolicyBinding`)에 `priority` 숫자로 표현한다. **위가 이긴다.**

```
[대량등록 모드]                        [모음전 모드]
 6  개별 상품 (draft)                   6  구성 (set)
 5  구성 (소싱처 × 브랜드)               5  상품 (model)
 4  검색필터                    ← 신설
 3  소싱처 카테고리              ← 신설
 1  기본 정책 (is_default)               1  기본 정책
```

**항목 단위로 이긴다** — 정책 통째가 아니라 13항목 **하나하나** 위층 값이 있으면 그것을 쓴다.
🔵 우리는 이미 `from_common_at`(항목 단위 값 출처)을 갖고 있다(우위 12번). **더망고는 정책 단위뿐이다.**

**🔴 그래서 「정책 출처 표시」(채택 12)는 상속과 한 몸이다.**
상속을 켜는 순간 「이 값이 왜 이렇지?」를 못 풀면 사고가 난다.
→ 화면에 **「이 값은 〈검색필터: 무신사_나이키〉에서 왔습니다」**를 항목마다 띄운다.

**정책을 고치면 몇 개가 바뀌는지 먼저 보여준다** (§03:116) — 소급 적용 전 **영향 상품 수** 표시.

### 8-1. 🔴 「지금 손실 중」의 정확한 위치 — **두 개를 섞지 말 것**

앞선 문서(§08-17)의 *"옵션 71개 상품이 10개만 나간다 — 지금 손실 중"* 은
**더망고에서** 나는 손실이다(마인드맵 원문: *「전송 옵션개수 = 10개」·「옵션명 오름차순 앞 N개」*).
**우리 코드에는 옵션 상한 규칙이 아예 없다** — `lemouton/` 전체에 옵션 개수를 자르는 코드 0건.
우리 원칙이 「실측값만 적용, 모르면 미적용」(🔵우위 8번)이기 때문이다.

| | 어디서 새나 | 우리에게 뜻하는 것 |
|---|---|---|
| **옵션 71→10 잘림** | 🟠 **더망고 쪽** | 우리로 옮겨올 때 **같은 손실을 물려받지 않게** 규칙을 새로 세운다 |
| **롯데온 본보기 복사** | 🔴 **우리 코드** (`compile_more.py:148`) | 대량으로 밀면 **되돌릴 수 없다.** 우리 유일한 실물 폭탄 |
| 재고 상한·중복 방어·옵션불가 카테고리 | ⚪ 아직 아무 규칙 없음 | 규칙이 없는 것 = 마켓이 대신 정하게 두는 것 |

**Phase 2 를 3보다 앞에 둔 이유** — 정책 합치기는 크고 오래 걸린다.
그 사이에 **되돌릴 수 없는 사고**(롯데온)가 한 번 나면 수천 건을 지우고 다시 올려야 한다.
**되돌릴 수 있는 미완성보다 되돌릴 수 없는 사고가 먼저다.**

### 8-2. ⚠️ 채택 15(옥션·G마켓 옵션등록 불가 카테고리) — **근거 데이터가 없다**

구현하려다 막혔다. **채택 판정을 정정해야 한다.**

**실측 — ESM 카테고리 API 응답에 「옵션 등록 가능 여부」 칸이 자체가 없다.**
`/item/v1/categories/site-cats` 가 주는 칸은 `catCode` · `catName` · `isLeaf` 셋뿐이다
(`marketplace_api_map.json` · 수집기 `category_harvest.py:279 harvest_esm_site`).
sd-cats·site-cats 매칭 API 도 같다.

**더망고도 API 로 아는 게 아니었다.** 그쪽 화면 이름이 **「단일상품등록설정」**이다 —
**사람이 넣는 목록**이다(마인드맵 L2 「상품관리관련·마켓 관리정보 설정」).

→ 목록을 우리가 지어내면 **없는 근거로 등록을 막는 것**이 된다.
「실측값만 적용, 모르면 미적용」(🔵우위 8번)의 정면 위반이다. 그래서 **지금은 안 만든다.**

**대신 지금 할 수 있는 것 (근거 100%)** — 우리는 옵션 부착 실패를 **이미 잡고 있다**
(`send_more.py:161~178` — 실패하면 `PartialRegisterError` + 즉시 판매중지 회수).
그런데 **그 실패가 어느 카테고리에서 났는지는 아무도 기억하지 않는다.**
→ 실패 메시지에 **카테고리 코드를 싣는다.** 그러면 목록의 씨앗이 실측으로 쌓인다.

**나중에 고를 두 갈래 (사장님 판단 필요)**

| 안 | 방식 | 값 | 비용 |
|---|---|---|---|
| **가** | **실패에서 자동으로 배운다** — 옵션 부착이 실패한 (마켓, 카테고리)를 표에 쌓고 다음부터 preflight 가 막는다 | 🔵 **더망고보다 낫다**(사람 입력 불필요·근거는 마켓 응답) | 새 표 1개. **첫 한 번은 못 막는다** |
| **나** | 사장님이 목록 입력 (더망고 방식) | 첫 번째부터 막는다 | 설정 화면 1개. 근거가 **사람 기억** |

권장 = **가 + 나 겸용.** 자동으로 쌓되 사람이 손으로 더할 수 있게.
단 **Phase 4 이후**로 미룬다 — 지금은 근거가 0건이라 만들어도 아무것도 막지 못한다.

## §12. [2026-08-08] 소싱처 확대 · 「뺄 옵션」 · 성적표 구현 (PR#925)

### 12-1. 소싱처는 8곳이 천장이다 (🔴 설계 전제 정정)

「소싱처를 넓히자」에서 처음 적은 후보는 ABC마트·GS샵·29CM·패션플러스였다.
**틀렸다.** `sourcing/crawlers/__init__.py::build_crawlers` 가 아는 곳은 8곳뿐이고,

조용한 0건이 된다. → 규칙은 **크롤 가능한 곳에만** 넣도록 시험으로 못박았다.

| 소싱처 | 리스팅 규칙 | 페이지 넘김 |
|---|---|---|
| 무신사 | ✅ (기존) | ✅ `page` |
| SSF | ✅ 브랜드칸 포함 | ✅ `currentPage` (카테고리 목록만) |
| 롯데온 | ✅ 묶음 제외 | ❌ 무한 스크롤 |
| 롯데아이몰 | ✅ | ❌ 무한 스크롤 |
| 현대H몰 | ✅ 속성에서 | ❌ |
| SSG | ❌ 미측정 (앱 브라우저 차단 + 서버 403) |
| 르무통 · 스스르무통 | ❌ 미측정 (로그인 필요) |

### 12-2. 확장에 규칙이 박혀 있으면 서버를 고쳐도 소용없다

`_listingCollectIds` 가 무신사 전용이었다. 「규칙을 넣었다」와 「그 규칙이 쓰인다」는
다른 사실 — 이 저장소에서 세 번째로 같은 모양이다(대기열 · SetChannel · 이번).
→ 규칙을 **서버가 내려준다**(`sel`·`attr`·`id_re`). 다음 소싱처는 확장 수정 0.

### 12-3. 남은 것

- SSG · 르무통 계열 리스팅 규칙 (실측 수단부터 필요)
- 무한 스크롤 소싱처는 **첫 화면분만** 걷힌다(롯데온 48 · 아이몰 26 · SSF 27).

- 「구성별 자동화 예외」(`auto_mode`·`manual_crawl_hours` 등)는 여전히 **전혀 안 먹는다.**

## §13. [2026-08-08] 훑기 정직성 · 무한 스크롤 · 찾은 주소 보기

### 13-1. 🔴 보내는 쪽이 정직해도 받는 쪽이 버리면 소용없다

확장은 「한 장이 실패한 걸 0건과 구분해야 한다」며 실패 사유(`error`)를 늘 실어
보냈다. **서버가 그 값을 받기만 하고 버렸다** — 저장도 표시도 없었다.
그래서 「페이지가 안 열렸다」가 화면에선 「끝남 / 0건」과 **똑같아 보였다.**

같은 부류가 이 저장소에서 세 번째다 — 대기열(넣었는데 꺼내는 쪽이 다른 기준),
SetChannel(쓰는 곳과 읽는 곳이 다름), 이번(보내는데 받는 쪽이 버림).
**「A가 한다」와 「B가 그걸 쓴다」는 항상 따로 확인한다.**

### 13-2. 세 가지를 갈라 말한다

| 화면 | 뜻 |
|---|---|
| 끝남 | 다 봤고 그게 전부다 |
| **못 봄**(빨강) | 페이지를 못 열었다 — 0건이 아니다 |
| **더 있음**(주황) | 정해진 만큼만 내려 봤다 — 더 있을 수 있다 |

뭉치면 사장님이 **없는 상품을 없다고 믿는다.**

### 13-3. 🔴 「무한 스크롤」이 아니었다 — 내 진단이 틀렸다

처음엔 「페이지 넘김 파라미터가 없으니 무한 스크롤이겠다」고 보고 스크롤을 넣었다.
**실측하니 셋 다 안 통했다** — 롯데온 48→48 · 롯데아이몰 24→24 · 현대H몰 40→40.
(H몰은 몸통이 스크롤 대상이 아니라 **안쪽 상자**를 내려야 했는데, 그것까지 해도 그대로.)

셋 다 **단추를 눌러 넘기는** 방식이다. 롯데온에서 「2」를 눌러 보니 주소는 안 바뀌고
상품만 바뀌었다 — 그래서 주소 파라미터로도, 스크롤로도 못 넘긴다.

★ **파라미터가 없다 ≠ 무한 스크롤.** 「어떻게 넘기나」는 직접 눌러 봐야 안다.

지금 할 수 있는 정직한 일은 하나 — **「더 있다」를 말해 주는 것.**
「다음」 단추가 살아 있으면 우리가 첫 장만 가져온 것이므로 `capped` 로 알린다
(실측 확인: 롯데온 48건 + 더있음 · 아이몰 24건 + 더있음).
단추를 눌러 여러 장을 걷는 일은 **다음 걸음**이다.

### 13-4. 「찾은 주소 보기」

화면은 「찾음 31」이라고만 말했다. **무엇을** 찾았는지 볼 방법이 없어, 검색어가
엉뚱해 잡화가 딸려 와도 상품을 만들어 보기 전엔 몰랐다.
주소마다 **어디까지 왔는지**(크롤 전 / 크롤됨 / 상품됨)도 같이 말한다.

### 13-5. 🔴🔴 「결과 0건」 화면에도 상품이 깔려 있다 (가장 위험했던 것)

「검색 결과가 없습니다」가 떠 있는 화면에서 우리 규칙에 잡힌 수 — **6곳 중 5곳**:

| 소싱처 | 잡힌 수 | 정체 |
|---|---|---|
| 무신사 | 19 | 회원가입 이벤트 상품 |
| 롯데온 | 25 | 추천 |
| 롯데아이몰 | 25 | 메뉴 속 배너 |
| 현대H몰 | 12 | 실시간 베스트 |
| 르무통 | 1 | 상단 노출 |
| SSF | **0** | — 여기만 정직 |

처음엔 롯데 3사만인 줄 알았다. **「우리 첫 소싱처(무신사)는 괜찮겠지」가 틀렸다.**
그대로 뒀으면 **사장님이 오타 한 번 낼 때마다 엉뚱한 상품 수십 건이 크롤 대기에
들어가 초안까지 되고 마켓으로 갔다.**

더 나쁜 것 — **롯데아이몰은 정상 검색어에서도 전부 가짜였다.**
`a[href*=viewGoodsDetail]` 25건이 통째로 메뉴 속 추천 배너였고, 진짜 결과는
`data-goods-no`(나이키 60건)였다. **정상 검색어 하나만 봤을 땐 26건이 그럴듯해서
못 알아챘다** — 0건 검색어로 대조하고서야 드러났다.

★ 규칙을 넣기 전 **두 번 잰다** — ①흔한 검색어 ②없을 법한 검색어.
  ②에서 0이 아니면 규칙이 결과 영역 밖을 보고 있는 것이다.
★ 「결과 없음」 글귀를 가드로 두되, **글귀가 없다고 0건으로 만들지는 않는다**
  (UI 가 바뀌면 멀쩡한 수집이 통째로 죽는다). 있을 때만 「없다」고 확정한다.

### 13-6. 단추로 넘기는 소싱처도 여러 장을 걷는다

13-3 에서 「단추를 눌러 걷는 일은 다음 걸음」이라 적었던 것을 같은 날 이어서 했다.

| 소싱처 | 첫 장 | 5장 걷은 뒤 |
|---|---|---|
| 롯데온 | 47 | **283** |
| 롯데아이몰 | 60 | **300** |

★ **칸을 새로 만들지 않았다.** 사장님 화면의 「몇 쪽부터 / 몇 쪽까지」를 그대로 쓴다 —
  주소로 넘기는 곳은 주소를 만들고, 단추로 넘기는 곳은 그만큼 누른다.
  같은 뜻인데 칸이 둘이면 어느 쪽을 채워야 할지 모른다.

🔴 주소로 넘길 수 있는 곳은 **누르지 않는다** — 둘 다 하면 같은 상품을 두 번 걷는다.
🔴 눌렀는데 안 늘면 **중단한다** — 안 넘어간 채로 계속 누르면 같은 장을 헛돈다.
🔴 상한은 `MAX_PAGES`(20). 실수로 9999 를 넣으면 소싱처를 두들긴다(차단 위험).

★ 곁가지 수정 — `page_urls_for` 가 「넘김 규칙을 모르는 곳」에 범위를 주면 **예외**를
  냈다. 그러면 범위를 적은 순간 **첫 장조차 못 걷는다.** 걷을 수 있는 데까지는 걷게 했다.

### 13-7. 🔴🔴 무신사 `page=` 는 서버가 아예 무시하고 있었다

사장님 말씀 — 「무신사 같은 경우 몇천개도 돼」. 재 보니 「나이키」가 **2,412개**였다.
그런데 우리 규칙은 `page=` 로 넘긴다고 적혀 있었고, **그건 거짓이었다.**

- `page=1` 과 `page=2` 의 응답이 **상품번호까지 완전히 동일**(둘 다 `totalCount 2412`)
- 렌더된 화면도 1쪽·2쪽·50쪽 첫 상품이 전부 같았다
- 그대로 뒀으면 「5쪽까지」로 시켜도 **같은 1쪽을 5번 긁고 「5장 봤다」**고 말했다

**진짜 창구** — 검색 페이지 HTML 안에 목록 응답이 통째로 들어 있고, 거기 `pagination`
안에 `nextPageUrl` 이 있다. 그걸 따라가면 쪽당 60개씩 41쪽, 2,412개가 전부 나온다.

🔴 **주소를 우리가 조립하면 안 된다.** `hmacId` 라는 서명이 붙어 있어 `page=41` 로
손수 바꿔 부르면 **403 「잘못된 접근입니다」**가 온다(실측 확인). 받은 주소 그대로 따라간다.

실측 — 6쪽 돌려 **47 → 347개**. 상한 `MAX_PAGES` 20 → **60**(무신사 기준 3,600개까지).

★ 배운 것 — **「페이지 파라미터가 있다」와 「그게 먹는다」는 다른 사실이다.**
  파라미터 이름이 주소에 보인다고 넘어가는 게 아니다. 1쪽과 2쪽을 **대조해야** 안다.

### 13-10. 🔴 SSF — 같은 소싱처인데 주소 종류에 따라 다르다

### 13-11. 아직 못 푼 두 곳

- **현대H몰** — 사장님 크롬에서 안쪽 스크롤 상자를 바닥(7213/8050)까지 내리고
  휠 이벤트까지 흉내 냈지만 36 → 37 이 전부. 네트워크 요청도 안 떴다.
  **진짜 마우스 휠**이라야 반응하는 구조로 보인다.
- **SSG** — 앱 브라우저·사장님 크롬 연결 **둘 다 정책 차단**. 접근 방법이 없다.
  2쪽으로 넘긴 뒤의 주소를 받으면 규칙을 만들 수 있다.

### 13-12. 🔴🔴 현대H몰이 풀렸다 — 「스크롤이 필요한 곳」이 아니었다 (PR#981)

13-11 의 진단(**「진짜 마우스 휠이라야 반응한다」**)은 **틀렸다.**
`page=3` 을 열어 두 가지를 따로 재 보니 이렇게 갈렸다.

| 무엇을 보나 | 몇 개 | 어느 쪽 |
|---|---|---|
| 화면(DOM `[data-slitm-cd]`) | 36개 | **1쪽** |
| 받은 글(HTML `"slitmCd":`) | 36개 | **3쪽** |
| 두 집합의 겹침 | **0개** | — |

서버는 3쪽을 정확히 보내 주는데, 브라우저 안의 앱이 뜨자마자 **1쪽을 다시 불러
화면을 덮어쓴다.** 그래서 화면만 보면 6쪽을 시켜도 늘 같은 36개다.

→ 규칙에 `html_scan`(`_HTML_SCAN = {'hmall'}`) 을 신설했다. **H몰만** 받은 글에서 읽는다.

★ 다른 곳은 그대로 **화면에서 읽는다.** 화면에서 읽으면 「눈에 보이는 것과 같다」는
  장점이 있어(화면에 없는 배너·광고가 안 딸려 온다) 추측으로 넓히지 않는다.

★★ 배운 것 — **「화면에 안 보인다」가 「안 왔다」는 뜻이 아니다.**
   스크롤을 흉내 내기 전에 **받은 글부터 뒤져 볼 것.** 13-11 은 이 순서를 건너뛰어
   없는 「휠 문제」를 쫓느라 `chrome.debugger` 통로까지 만들었다가 걷어냈다.

### 13-13. 🔴🔴 확장은 **세 곳**이 따로 논다 — 두 번 헤맨 함정 (PR#981)

| 층 | 어디 | 어떻게 바꾸나 |
|---|---|---|
| 저장소 | `extension/moum-crawler/` | 코드 → PR → 머지 |
| 라이브 서버 | Fly.io | 배포 |
| **크롬이 읽는 폴더** | 사장님 바탕화면 `moum-crawler-v0.7.63` | **손으로 복사** |

- 폴더 **이름이 `v0.7.63`** 이라 이름으로 판번호를 판단하면 안 된다
- `chrome://extensions` 의 **↻ 는 그 폴더를 다시 읽을 뿐**이다. 폴더가 옛 판이면 아무 일도 없다
- 🔴🔴 **화면 새로고침(F5)은 확장 본체를 안 바꾼다.** 화면 쪽(`content_mou.js`)만 새로
  붙어 `data-moum-ext` 는 **새 판**을 보여 주는데, 일하는 본체(서비스워커)는 **옛 판**이다
  → 「확장 0.7.92 맞음」을 근거로 멀쩡한 코드를 의심하며 한참 헤맸다

**처방 2개**
1. 확장이 결과에 **자기 판 번호(`ext_version`)를 실어 보낸다** → 화면에 「확장 0.7.9x」 표시.
   이제 **일하는 본체의 판**을 눈으로 확인할 수 있다
2. `scripts/sync_loaded_extension.py` — 로드 폴더를 저장소와 맞추는 한 줄 도구.
   덮기 전에 **origin/main 에 없는 줄**이 있으면 멈춘다(다른 세션 작업 보호)

### 13-14. 0건은 **무엇을 봤는지**까지 말해야 한다 (PR#981)

「상품이 없다」와 「우리 규칙이 안 맞는다」가 **똑같이 0으로 보인다.** SSG 0건에서 겪었다.
→ 0건이면 그 화면의 **제목·링크 총수·우리 선택자에 걸린 수**를 함께 보낸다.

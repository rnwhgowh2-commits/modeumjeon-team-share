## 0. 왜 하는가 — 한 줄

지금 「옵션생성 → 상품생성 → 상품가공 → 정책생성 → 정책적용」을 다 해도 **마켓에 아무것도
안 올라간다.** 정책값 중 밖으로 나가는 것은 판매가·배송비뿐이고, 그마저도 *이미 등록된*
상품의 가격 갱신 경로다. 신규 등록은 `/bulk`(대량등록)이 **다른 정책표**(`ProcessRule`)로
따로 한다.

이 설계서는 그 끝을 잇는다 — **정책 붙인 구성을 골라 마켓으로 보내는 화면**을 만들고,
정책 13항목이 실제 전송 payload 가 되게 한다.

## 1. 사장님 확정 사항 (2026-08-02)

| # | 항목 | 확정 |
|---|---|---|
| ① | 목록의 한 줄 | **구성(벌) 1개 = 1줄** |
| ② | 「업데이트 항목」 | **둘 다 둔다** — 소싱처 다시 긁기 + 마켓으로 보내기 |
| ③ | 안전 필터 | **정책 안 붙음** · **마켓 등록됨/미등록** |
| ③-b | 전송 실패 | **실패 부류로 나눠 보여주고, 사유는 마켓 API 가 준 원문 그대로** |
| ④ | 날짜 필터 | **소싱처 수집날 / 마켓 전송날 골라쓰기** |
| ⑤ | 상단 탭 | 「자동화」 → **「상품 마켓 전송」** · 하위탭 2개 |

### ③-b 를 오해하지 말 것 — 사고 방지의 핵심

사장님 원문: *"발송 시 실패하면 발송 실패 부류에 맞게 설정하고 실패사유 보내기.
ex. 정책 필수 상품 누락으로 인한 마켓 전송 실패(**이 내용은 api 실제 마켓으로부터
전송 실패한 이유를 적어야함**)"*

즉 **두 칸으로 나눈다**:

- **부류(우리가 붙임)** — 「정책 필수 항목 누락」·「재고 확인 불가」·「계정 문제」 …
  사장님이 무엇부터 손볼지 정하는 데 쓴다.
- **사유(마켓이 준 원문)** — 마켓 API 응답의 **에러코드 + 메시지 그대로**.
  🔴 **우리가 지어내지 않는다.** 마켓이 아무 말도 안 했으면 「마켓이 사유를 주지
  않았습니다」라고 적는다. 그럴듯한 추측을 적으면 사장님이 엉뚱한 데를 고친다
  (프로젝트 최상위 원칙 · 폴백 금지).

  다행히 어댑터는 이미 원문을 들고 있다 —
  `adapters/smartstore.py:61` `error=f"{r.error_code}: {r.error_message}"`.
  지금은 그게 `MarketRegistration.sync_error` 한 칸에 뭉개져 부류와 섞인다.

## 2. 배선 — 정책 13항목이 어떻게 마켓까지 가나

### 2-1. 지금 (PR#678 이 진단한 그림)

```
 MarketPolicyValue (13항목 × 6마켓)
        │
        └─ as_template.py ──▶ 판매가 · 배송비  ──▶ 가격 엔진 ──▶ 이미 등록된 상품 갱신
           (나머지 11항목은 읽는 코드가 0곳 — 저장만 됨)

 ProductDraft + ProcessRule ──▶ compile_* ──▶ 마켓 신규 등록   ← 완전히 다른 길
```

### 2-2. 이렇게 잇는다

```
 구성(ProductSet) ──┬── SetPolicyLink ─┐
                    └── 상품 정책 ─────┴──▶ MarketPolicy (13항목 × 마켓)
                                                 │
                                    policy/to_payload.py  ← 신규
                                                 │
                              ┌──────────────────┴──────────────────┐
                       마켓 상품번호 없음                     마켓 상품번호 있음
                     (SetChannel.market_product_id)                 │
                              │                                     │
                       신규 등록 payload                      수정 payload
                       compile_smartstore/coupang/more        uploader/adapters
                              └──────────────────┬──────────────────┘
                                                 ▼
                                      SendJob / SendJobRow (신규)
                                      부류 + 마켓 원문 사유 기록
```

### 2-3. 🔴 정책표 두 벌 문제 — 어느 쪽이 이기나

이 저장소에는 **가공 규칙 표가 두 벌**이다.

| | `ProcessRule` (대량등록) | `MarketPolicyValue` (정책 생성) |
|---|---|---|
| 붙는 대상 | 소싱처 × 브랜드 | 상품 / 구성(벌) |
| 쓰는 화면 | `/bulk` 데이터 가공 | `/policies` |
| 마켓 축 | 있음 (공통 + 마켓별) | 있음 (마켓 공통 + 마켓별) |
| 항목 정의 | `process_rule_schema.all_schemas()` ← **원천** | 같은 것을 불러 씀 |

**확정: 이번 화면은 `MarketPolicyValue` 만 본다.**
`ProcessRule` 은 크롤 초안(`ProductDraft`)에만 남긴다 — 초안은 소싱처×브랜드가 주인이라
붙일 구성 자체가 없기 때문이다. 둘을 섞으면 「어느 규칙이 이겼나」를 아무도 못 말한다.

항목 **정의**는 이미 한 곳(`process_rule_schema`)을 공유하므로 갈리지 않는다.
갈리는 것은 **값**뿐이고, 값의 주인을 화면별로 하나씩 못 박는다.

### 2-4. 되받기 사슬 (위가 이긴다)

```
구성 정책(SetPolicyLink) → 상품 정책(BundlePolicyLink) → 쓰던 가격 템플릿
```

`as_template.policy_template_for_set` 이 이미 이 사슬을 지킨다. `to_payload` 도 **같은
함수를 쓴다** — 여기서 사슬을 다시 쓰면 가격과 나머지 항목이 서로 다른 정책을 따르게 된다.

### 2-5. 항목별 배선 계획

| 항목 | 어디로 가나 | 1단계에 넣나 |
|---|---|---|
| 판매가 | 이미 감 (`as_template`) | 그대로 |
| 배송 | 배송비만 감 → 배송방법·출하지까지 | ✅ |
| 상품명 | 접두·접미·금지어·길이 → `name` | ✅ |
| 카테고리 | 마켓 카테고리 코드 | ✅ |
| 이미지 | 장수·비율·CDN | ✅ |
| 상세설명 | 머리말·꼬리말·금지 태그 | ✅ |
| 옵션 | 축 구성(1/2/3축) | ✅ |
| 고시정보 | 상품군 + 항목값 | ✅ |

## 4. 마켓 전송 화면 (`/market-send`)

더망고 「상품 업데이트 & 마켓등록/수정」의 구조를 따르되, 우리 데이터 모델에 맞춘다.

### 4-1. 필터 (사장님 확정 반영)

| 자리 | 칸 | 더망고 | 우리 |
|---|---|---|---|
| 1줄 | 날짜 기준 드롭다운 + 범위 + 켜기 체크박스 | 등록일자 | **소싱처 수집날 / 마켓 전송날** 골라쓰기 (④) |
| 2줄 | 마켓 등록 여부 | 마켓등록/미등록 | 그대로 (③) |
| 2줄 | **정책 붙음 여부** | 없음 | **신규** (③) — 안 붙은 것만 / 붙은 것만 / 전체 |
| 2줄 | 재고 상태 | 판매상품(재고+품절) | **3상태** — 재고 있음 / 품절(0) / **확인 불가** |
| 2줄 | 이름 검색 | 상품명 검색 | 상품명 · 모음전 번호 · 마켓 상품번호 |
| 3줄 | 소싱처 체크박스 | 12개 | 우리 소싱처 목록 |
| 4줄 | **긁을 항목** | 업데이트 항목 | 가격 / 재고 / 이미지 / 상세설명 (②) |
| 5줄 | **보낼 항목** | 없음 | 가격 / 재고 / 이미지 / 상세설명 / 옵션 (②) |
| 6줄 | 보낼 마켓 체크박스 | 6개 | 6개 |

**②「둘 다 둔다」의 뜻** — 「긁을 항목」은 서버가 못 한다(크롤=로컬 PC 원칙). 누르면
**내 PC 크롬 확장에 일감을 보내고**, 끝나면 「보낼 항목」이 마켓으로 나간다.
크롬이 안 켜져 있으면 **그 사실을 말하고 멈춘다** — 조용히 건너뛰면 옛 값이 나간다.

### 4-2. 목록 (한 줄 = 구성 1개 — 확정 ①)

| 칸 | 내용 |
|---|---|
| No | |
| 소싱처 | 그 구성이 물고 있는 소싱처들 |
| 상품 / 구성 | 모음전 번호 · 이름 · **구성 이름(= 정책 이름)** · [옵션개수:N] |
| 정책 | 붙은 정책 이름 (없으면 빨강 「없음」) |
| 소싱처 수집 | 마지막 수집 시각 |
| 마켓 전송 | 마켓별 마지막 전송 시각 (칩) |
| 개별 | 「긁기&전송」 버튼 |

정렬 — 더망고와 같이 **마켓별 전송 날짜순**까지 (`MarketRegistration.last_success_at`).

### 4-3. 실행

- 「긁기&전송 시작 (검색결과 전부)」 / 「범위 설정」 두 버튼 (더망고와 같은 자리)
- 🔴 **마켓 간 병렬 금지** — 순차. 이 저장소의 속도정책(계정별 버킷·ESM 5초/1회)을 따른다
- 🔴 **부분 성공 허용** — 한 마켓 실패가 다른 마켓을 막지 않는다. 마켓마다 결과를 커밋

### 4-4. 실패 부류 + 마켓 원문 사유 (확정 ③-b)

새 표 `send_job_rows`:

| 칸 | 뜻 |
|---|---|
| `kind` | **부류 (우리가 붙임)** — 아래 목록 |
| `market_code` | **마켓이 준 에러코드 원문** |
| `market_message` | **마켓이 준 메시지 원문** |
| `our_note` | 우리가 덧붙인 안내 (있으면) |

부류 목록 (전송 전 게이트에서 잡히는 것 + 마켓이 거부한 것):

| 부류 | 언제 |
|---|---|
| `NO_POLICY` | 정책이 안 붙음 — 보낼 값이 안 정해짐 |
| `POLICY_REQUIRED_MISSING` | 그 마켓 필수 항목이 비어 있음 (PR#678 표 사용) |
| `STOCK_UNKNOWN` | 재고 확인 불가 — 있다고 단정 못 함 |
| `NO_CATEGORY` | 마켓 카테고리 미확정 |
| `ACCOUNT` | 계정·인증 문제 |
| `MARKET_REJECTED` | **마켓이 거부** — 사유는 마켓 원문 그대로 |
| `NO_REASON_GIVEN` | 실패했는데 **마켓이 사유를 안 줌** (지어내지 않는다) |

**다음 사람에게** — 이 저장소에서 「없어서 만들어야겠다」 싶으면 먼저 찾아볼 것.

그대로 부를 수 있는지** 보라.

### 라이브 실측으로만 잡힌 함정 (테스트는 통과했다)

## 8. 다음 일감 — 구성에 없는 세 칸

신규 등록은 배선이 끝났지만 **대부분 preflight 에서 걸린다.** 구성에 아직 이 칸이
없기 때문이다.

| 없는 칸 | 왜 지어내면 안 되나 |
|---|---|
| 상품 이미지(CDN) | 스스는 네이버 CDN 주소만 받는다 — 외부 주소는 거부 |
| 고시정보 | 빈 고시가 마켓에 그대로 게시된다 |
| A/S 전화번호·안내 | **가짜 번호가 실제 판매 상품에 게시된다** |

`send/as_draft.py:missing_fields()` 가 이 셋을 사람 말로 알려 준다. 구성에 이 칸을
넣는 화면이 생기면 신규 등록이 실제로 통과한다.

## 1. 무엇을, 왜

「데이터 코드 지도」에 **개발 체크리스트** 탭을 소싱처·판매처 각각 신설한다.

**빈칸을 다 채우면 그 소싱처/판매처는 개발이 끝난 것**이 되게 한다. 지금은 새 마켓을 붙일 때
무엇을 해야 끝인지가 사람 머릿속에만 있고, 「코드는 있는데 실제로 되는지 모르는 것」과
「아예 안 만든 것」이 같은 얼굴을 하고 있다.

### 이 작업에 함께 포함하는 것 (사장님 확정 2026-08-12)

**할인 기준 마진 수정.** 체크리스트가 드러낸 문제이고 돈이 걸려 있어 같이 고친다. §7 참조.

## 1-B. 🔴 이미 있는 것 — 다시 만들지 않는다 (2026-08-12 origin/main 실측)

설계 도중 origin/main 이 `11ca5add` 로 움직였고, **다른 세션이 체크리스트의 데이터 층을 거의 다 만들어 두었다.**
새로 만들 것은 **화면과 소싱처판**이고, 판정 근거는 아래를 **그대로 읽는다**.

| 이미 있는 것 | 무엇을 담고 있나 |
|---|---|
| `lemouton/policy/required.py` | **16항목 × 6마켓 = 96칸** 「마켓이 등록 때 요구하는가」 판정 + **등록 API 원문 근거** + 4상태(필수/조건부/선택/확인불가) |
| 〃 `SOURCE_API` | 마켓별 **상품등록 API** 가 무엇인지 (근거의 출처) |
| 〃 `WIRING` / `wiring_of()` | 그 항목이 **실제로 마켓에 나가는가**(WIRED) vs **저장만 되는가**(STORED_ONLY) |
| 〃 `TO_VERIFY_BY_LIVE` | **실등록으로만 확인 가능한 6칸** |
| `lemouton/registration/market_limits.py` | 마켓별 **상품명 상한** — 확인된 것만, 확인 불가는 이유까지 |
| `process_policy.ITEM_KEYS` | **16항목** (기존 13 + `listing` · `price_compare` · `ids`) |

🔴 **내가 하려던 「API 지도에서 키워드로 필드 뽑기」는 버린다.** `required.py` 가
사람이 검증한 등록 API 원문을 이미 갖고 있고, 키워드 매칭보다 훨씬 정확하다.
(키워드 방식은 「상품번호」가 「품번」에 걸리는 등 거짓양성이 났다.)

## 4. 칸 값 — 5단계

체크리스트가 답해야 하는 물음은 **「이 값을 이 마켓에 제대로 보낼 수 있나」** 다.
그러려면 **두 축**을 함께 봐야 한다 — ① 마켓이 요구하는가(`required.py`) ② 우리가 실제로 보내는가(`WIRING`).

| 표시 | 뜻 | 자동으로 어떻게 판정하나 |
|---|---|---|
| ⬜ 미착수 | 우리 프로그램에 칸이 없거나, 마켓 근거를 못 찾음 | 매핑된 항목 없음 **또는** `status_of == UNKNOWN` |
| 🟡 저장만 됨 | 칸도 있고 마켓도 받는데 **보내는 코드가 없음** | 항목 있음 + `wiring_of == STORED_ONLY` |
| 🟢 검증완료 | 실제로 나가고 실계정으로 확인함 | `wiring_of == WIRED` + 손보정 검증일 있음 |
| ⚫ 불가 | 그 마켓에 기능 자체가 없음 | 엑셀 값이 `X` |
| ➖ 해당없음 | 그 마켓엔 해당 항목이 없음 | 엑셀 값이 빈칸 또는 `-` |

🔴 **「🟡 저장만 됨」이 이 표의 핵심이다.** 지금 정책 16항목 중 **14개가 여기 있다** —
사장님이 값을 다 채워 넣어도 **판매가·배송비 말고는 마켓으로 나가지 않는다.**
이걸 화면이 말하지 않으면 「채웠는데 왜 안 바뀌지」로 헤매게 된다.

### 4-1. 자동 산출의 원천

| 축 | 원천 |
|---|---|
| 마켓이 요구하는가 + 근거 원문 | **`lemouton/policy/required.py::status_of(market, item)`** |
| 우리가 실제로 보내는가 | **`required.py::wiring_of(item)`** |
| 어느 API 로 보내나 | `required.py::SOURCE_API` (마켓별 상품등록 API) |
| 마켓별 상한(상품명 등) | `lemouton/registration/market_limits.py` |
| 우리 프로그램 항목 | `process_policy.ITEM_KEYS` 16개 |
| 실등록으로만 확인 가능한 칸 | `required.py::TO_VERIFY_BY_LIVE` |
| 우리 기준 | 엑셀 머리글의 `▶` 뒤 문장 |
| 소싱처 로그인 여부 | `webapp/routes/accounts.py` 의 소싱처 `needs_login` |

**엑셀 25열 ↔ 프로그램 16항목 매핑이 필요하다.** 엑셀이 더 잘게 쪼개져 있다
(예: 프로그램의 `listing` 하나 = 엑셀의 과세·상품상태·판매기간·미성년자·제조사 5열).
가로축은 **엑셀 25열을 그대로 두고**, 각 열이 어느 프로그램 항목에 붙는지를 표로 고정한다.

### 4-2. 손보정 (사람이 다는 것)

`webapp/data/dev_checklist.json` 한 장에만 둔다.

- **실계정 왕복 검증일** — 코드로는 알 수 없다
- **불가 사유** — 「원래 안 되는 것」을 영원한 빨간불로 두지 않기 위해
- **문서 수집 상태** — 롯데온처럼 문서가 안 모인 곳

🔴 **자동값과 손값이 어긋나면 상단 배너로 알린다.** 조용한 통과 금지.
드리프트 계산은 기존 `webapp/routes/guide_sync.py` 패턴을 그대로 따른다.

### 4-3. 어긋남 표시 (빨간 `!`)

기계 판정만 한다. 추측하지 않는다.

| 조건 | 문구 |
|---|---|
| 엑셀이 `X`·`-`·빈칸인데 마켓 문서에 `[필수]` 필드가 있음 | 마켓 문서는 [필수]라는데 우리는 안 쓰기로 돼 있습니다 |
| 엑셀에 값이 있는데 마켓 문서에서 필드를 못 찾음 | 우리는 넣기로 했는데 마켓 문서에서 해당 필드를 못 찾았습니다 |

## 5. 화면 (시안 확정 2026-08-12)

정본 시안 = 바탕화면 `모음전 시안 v4 - 개발 체크리스트 확정.html`

### 5-1. 표

- 엑셀과 같은 격자. **마켓 이름 열은 왼쪽에 고정**(가로로 끝까지 밀어도 안 움직임 — 실측 0px)
- 머리글 2단(묶음 > 항목). 우리 기준이 정해진 항목엔 파란 `▸`
- 마켓 이름 옆에 **진행 막대 + 「n/m」**(숫자는 자릿수 맞춤)
- 어긋난 칸엔 빨간 `!`

### 5-2. 마우스 올리면 뜨는 정보창 — **필드 표형**

내용 순서 (위 → 아래):

1. 마켓 · 항목명 + 상태 배지 — 14px
2. **우리 기준** — 파란 칸 (사장님이 정하신 것이라 색으로 구분)
3. **마켓 문서가 요구하는 것** — 표: `필드명 / 필수 / 마켓 문서 원문`
   - 접었을 때 `[필수]` 필드만, 나머지는 **「나머지 n개 더 보기」**
   - 문서가 안 모인 마켓은 **비워 두고 그렇게 적는다**(지어내지 않는다)
4. **우리 프로그램 항목** — 없으면 「없음 — 만들어야 함」
5. **보낼 주소** — 복사 단추
6. 미착수·코드만이면 **왜 그런지 한 줄**
7. 맨 아래 근거 줄 — 묶음 · 지도 상태 · 필드 수(필수 n)

### 5-3. 정보창 규칙 (`hover-info-card` 표준 그대로)

| 규칙 | 값 | 실측 확인 |
|---|---|---|
| 화면 기준으로 띄움(표 밖) | `body` + `position:fixed` | 🟢 |
| 마우스가 떠나도 기다렸다 닫기 | 250ms | 🟢 |
| 정보창에 들어가면 닫기 취소 | — | 🟢 건너가도 내용 안 바뀜 |
| 촘촘한 격자라 열기도 지연 | 140ms | 🟢 빠르게 훑으면 안 열림 |
| 화면 아래쪽이면 위로 뒤집기 | 간격 7px · 여백 8px | 🟢 |
| 표를 옆으로 밀면 닫기 | — | 🟢 |
| 「더 보기」로 커지면 자리 다시 잡기 | — | 🟢 화면 밖으로 안 나감 |

칸을 **누르면** 오른쪽에 고정된다(두 칸 비교용). **좁은 칸이라 표형이 아니라 흐름형**으로 그린다.

## 7. 함께 고치는 것 — 할인 기준 마진

### 7-1. 지금 무엇이 잘못됐나

`lemouton/pricing/unified.py::compute_sale_price_unified` 는 **할인 인자를 아예 받지 않는다.**
`lemouton/policy/discount.py` 의 즉시할인은 계산과 무관하게 따로 실려 나간다.
그래서 마진율은 **할인 전 판매가** 기준으로 잡히고, 할인은 그 위에서 깎여 **깎인 만큼 마진이 사라진다.**

### 7-2. 사장님 확정 규칙

> **마진 기준가 = 판매가 − 판매자 부담 할인액** (마켓 부담분은 우리 수입이므로 빼지 않는다)

| 할인 종류 | 마진 기준 | 담을 칸 |
|---|---|---|
| 판매자 부담 100% (노출용 할인·쿠폰) | **할인가** | `price.discount_value` |
| 마켓 부담이 섞인 할인 (롯데온·G마켓 등) | **판매가** | `_site_discount` (**이미 있음**) |

### 7-3. 가격비교 수수료

가격비교 노출은 **항상 켠다**(사장님 확정). 롯데온은 프로그램에서 제휴 여부로 판단한다.

| 마켓 | 기본 요율 | 제휴 2% 포함 |
|---|---|---|
| 롯데온 18% · 옥션 15% · G마켓 15% | | 🟢 `fee_defaults.NOTES` 에 명시 |
| **11번가 11%(1년 이내 8%)** | | 🔴 **표기 없음 — 확인 필요**(엑셀엔 2%라 적혀 있음) |
| 스마트스토어 6% · 쿠팡 11.55% | | ➖ 해당 없음 |

|---|---|
| 🟢 나감 (WIRED) | **판매가 · 배송** (배송도 배송비만) |
| 🟡 저장만 됨 (STORED_ONLY) — **14개** | 상품명 · 카테고리 · 옵션 · 이미지 · 상세설명 · 고시정보 · 브랜드 · 원산지 · KC인증 · 금지어 · 태그 · 등록 기본값 · 가격비교 노출 · 모델번호·바코드 |

**「미착수 41칸 채우기」의 실제 정체가 이것이다** — 항목을 새로 만드는 일이 아니라
**저장된 값을 마켓으로 내보내는 배선**이다. 항목은 이미 다 있다.

### 8-2. 실등록으로만 확인 가능한 6칸 (`TO_VERIFY_BY_LIVE`)

| 마켓 / 항목 | 왜 |
|---|---|
| 롯데온 / 거의 전부 | 등록 문서가 요약본이라 문서로는 영영 못 정함. 실등록이 유일한 길 |
| 11번가 / KC인증 | 문서는 [필수]인데 우리 XML 은 이 칸 없이 등록 성공(2026-07-21) |
| 스마트스토어 / 배송 | 배송 정보를 통째로 안 보내면 「배송 없는 상품」이 되는지 |
| 쿠팡 / 원산지 | 원산지 단독 칸이 없음 — 고시정보 안에 넣는 게 맞는지 |
| 옥션 / KC인증 · 태그 | ESM 전문에서 칸을 못 찾음 |

⚠️ 확인 방법은 **일부러 그 칸만 비우고 등록을 시도**하는 것이다. 실제로 상품이 올라가므로
**등록 직후 반드시 판매중지로 되돌린다**(스스는 자동, 나머지는 수동). — 사장님 승인 후 진행.

### 8-3. 마켓별 상한

| | |
|---|---|
| 상품명 상한 확인됨 | 쿠팡 100자 · 11번가 100자 |
| **확인 불가** | 옥션 · G마켓(byte 기준이고 API마다 다름) · 롯데온 · 스마트스토어(등록 API 에 길이 선언 없음) |
| 아직 아무 데도 없는 상한 | 추가이미지 장수(11번가 3장) · 옵션 축 개수(롯데온 1~5, 프로그램 최대 3) · 상세설명 폭 · 태그 개수(쿠팡 20) |

### 8-4. 프로그램에 아직 없는 항목 — **1개**

사이즈(제품/포장). *(가격비교·상품상태·판매기간·과세·제조사·미성년자·모델번호·바코드 8개는
2026-08-12 다른 세션이 `listing`·`price_compare`·`ids` 로 추가 완료)*

### 8-3. 🔴 롯데온은 「불가」가 아니라 「문서 미수집」

API 118개 중 **응답 스펙 미확보 67개(57%)**. 다른 마켓은 0~3개.
`lotteon.product.create` 의 필드가 **2개**뿐이다. 25항목 중 **15항목이 필드 0개**.

이미 겪은 함정과 같은 자리다 — 롯데온 상품목록 API 도 `pageNo`·`rowsPerPage` 가 지도에 없어
「권한 없음」으로 오진했고, 그때 남긴 교훈이 **「지도의 params 를 '전부'로 믿으면 안 된다」** 였다.

### 8-4. 🔴 쿠팡은 지도와 실제가 어긋난다

지도상 `st == ok` 인 쿠팡 API 가 1개뿐인데, `capabilities.py` 에는 가격·재고가 `verified=True` 로 있다.
**두 원천을 합쳐 판정**하고, 어긋나면 배너로 알린다.

### 8-5. 🔴 방향(`dir`) 값이 망가져 있다

`receive` 165 · `recv` 57 — 같은 뜻이 두 이름. 그리고 **오태깅**:
`eleven11.40 "다중 상품 재고 정보 조회"` 가 `dir=send`, `eleven11.900 "판매가 변경"` 도 `send`.
받기/보내기 축을 세우려면 **정규화 + 「조회인데 send」 가드**가 먼저다.

## 9. 미결

1. **엑셀 Z열(마켓 고유)을 「기타」에서 떼어 낼까** — 떼면 묶음 14 → 15
2. **11번가 요율에 가격비교 2%가 포함돼 있나** — 안 포함이면 마진이 2%p씩 덜 남고 있다
3. **`_winner` 항목의 선택지가 실제 API 와 다르다** — 프로그램은 「최저가 −1원」 같은 규칙,
   쿠팡은 `autoPricingInfo.active` + `minSalePrice` 만 받는다. 배선할 때 API 모양으로 고쳐야 한다
   (⚠️ **최초 등록 시 승인 요청 전에만** 입력·변경 가능)
4. **과세구분 — 해외구매대행일 때는?** (사장님이 엑셀에 남기신 물음)
5. **소싱처 `lotteon` 의 이름이 두 곳에서 다르다** — 계산쪽(`lemouton/sourcing/source_ids.py`)은
   롯데온으로 쓰는데, 화면 씨앗 목록(`webapp/routes/accounts.py`)은 **「롯데홈쇼핑」**으로 적혀 있다.
   같은 열쇠말이 두 이름을 갖고 있으면 체크리스트에서 어느 줄인지 헷갈린다 — 어느 쪽이 맞는지 확인 필요.

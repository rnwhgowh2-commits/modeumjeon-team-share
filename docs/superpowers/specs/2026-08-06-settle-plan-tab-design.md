# 정산예정금액 탭 설계 (주문관리 하위탭)

> 작성: 2026-08-06 · 사장님 확정(2차 승인 — 재검토 보강 5건 반영)
> 목적: 기간별로 **앞으로 통장에 들어올 정산예정금**을 자금계획에 직접 쓸 수 있게 보여주는 화면.

---

## 1. 요구사항 (사장님 원문 요약)

- 주문관리 하위탭 「정산예정금액」 신설.
- 합산 대상 2부류, **절대 중복 금지**:
  1) 구매확정되어 정산받을 예정 금액
  2) 구매 미확정이나 송장번호 입력 기준 배송중/배송완료 → 앞으로 확정될 예정 금액
- 상품정산 + 배송비정산 분리 마켓은 **합산해서** 표시(배송비 포함 정산예정금액), 세부에서는 상품/배송비/총 3칸 별도.
- 기간은 **미래**. 마켓별 정산주기 전부 다름(쿠팡 최대 구매확정 후 2달). 스스·쿠팡 빠른정산 존재 — **각 마켓 1개 계정씩 빠른정산 사용 중**(계정별 스위치로 지정).
- 마켓별/계정별 세부 → 주문건까지 드릴다운.
- 추가 확정(질의 답변): 축 2개 — ① 지급예정일 기준(확정예정+미확정예정 구분, 자금계획용) ② 주문일 기준(클레임 제외 매출액 + 정산예정금액). 단위 일별+주별+월별. 「최종까지 기간 늘리면 총 얼마」 = 마켓총/마켓별/계정별/주문별 총 미수령 예정액.

## 2. 부류 4개 — 한 주문(라인)은 딱 한 곳 (중복 원천 차단)

| 부류 | 조건 | 표시 |
|---|---|---|
| 확정예정 | 주문상태=구매확정, 지급예정일 ≥ 오늘 | 기간표 본문 |
| 미확정예정 | 송장입력됨 + 배송중/배송완료 + 미확정 + 클레임 진행 없음 | 기간표 본문(확정과 구분 표기) |
| 기한경과 미확인 | 지급예정일 < 오늘인데 수령 확인 불가 | **별도 줄 상시 표시** (조용히 빼기 금지 — 구멍①) |
| 위험(클레임 진행) | 반품·교환·취소 진행 중 | 별도 줄, 예정액 제외 (구멍②) |

제외: 취소완료(`zero_cancel`), 클레임 행(`_kind=='change'`).

## 3. 지급예정일 결정 우선순위 (주문마다)

1. **마켓 실값** — 기존 30분 정산 스윕이 받아오지만 버리던 값을 `row` JSON에 저장 추가:
   - 쿠팡 `settlementDate` / 스스 `settleExpectDate` / ESM `RemitDate`
   - 저장 필드: `정산예정일` + 내부 태그 `_settle_date_source` = `real|estimated`
   - 기존 `_settle_source=='real'`인데 날짜 없는 행 → 1회 백필 스윕(기존 수동 스윕 라우트 재사용).
2. **규칙 추정** — 실값 없는 마켓(롯데온·11번가)·미확정 주문:
   - 예상 구매확정일 = 배송완료(관측 `status_at` 근사) + 마켓별 자동확정 일수. 배송중이면 +배송소요 추정.
   - 지급예정일 = 구매확정(예상)일 + 마켓별 정산주기.
   - **쿠팡 분할지급**: 추정 시 한 주문을 1차 지급분(약 70%)+잔여분(30%) 두 조각으로 나눠 각 예정일에 배치 (구멍③). 실값 있으면 실값 우선.
   - **빠른정산 스위치**: 계정별 boolean 설정(스스 1·쿠팡 1 계정 사용 중) → 켜진 계정은 빠른정산 주기로 계산.
3. **규칙표는 데이터로**: 마켓별 {자동확정 일수, 정산주기, 빠른정산 주기, 쿠팡 분할비율}을 편집 가능한 저장소(JSON/DB)에 두고 화면에서 보기·수정 (구멍④). 초기값은 구현 단계에서 마켓 문서+실측으로 채움.
4. **실측 자동 검증**: 저장된 실지급일 이력(RemitDate 등)과 구매확정일 간격을 역산해 규칙표와의 오차(일수)를 화면에 표시 — 추정이 실측에서 배우는 구조 (구멍④).

## 4. 금액 결정 우선순위 — 기존 로직 재사용 (신규 추정 엔진 금지)

1. `정산예정금(배송비포함)` (`_settle_source` ∈ real/store) — 그대로.
2. 없으면 기존 추정: `estimate_settle_from_history`(과거 실효 수수료율 역산) → 하드코딩 계수(롯데온·11번가). `_settle_source='estimated'`.
3. 배송비 분리 마켓(스스·11번가·쿠팡): 세부 화면에 상품/배송비/총 3칸. ESM·롯데온은 총액 단일 + 「분리 없음」 표기.
4. 재료 없음 → 0 + `none` 배지 (0으로 위장 금지, 배지로 정직 표기).

## 5. 축 2개 · 단위 3개

- **지급예정일 축**(기본): 세로=기간 버킷(일/주/월, 주=월~일), 가로=마켓 6개+합계. 각 칸 확정/미확정 구분.
- **주문일 축**: 클레임(취소·반품 완료분) 제외 **매출액=실결제금액 합**(빈 값은 상품금액+배송비 대체, **대체 건수 표기** — 구멍⑤) + 정산예정금액 합.
- KPI 카드: 총 미수령 예정액(=미래예정+기한경과, 각각 표기) / 확정예정 / 미확정예정.
- 드릴다운: 마켓 칸 → 계정별 → 주문별 목록(금액 3칸+배지+지급예정일+날짜근거).

## 6. 구현 배선 (탐색 실측 기준)

- 새 하위탭 key=`settle_plan` (🔴 삭제된 `i_sales` id 재사용 금지 — `_REMOVED_IDS`가 다시 지움):
  1. `webapp/routes/orders.py` `SUBTABS` 추가
  2. `webapp/templates/orders/index.html` `{% elif tab == 'settle_plan' %}` 블록
  3. `webapp/routes/api_sidebar.py` `_ITEM_DEFS` + `_STAGE_SPEC`(s_order) + **`_migrate_*` 신규 함수 + `_load()` 등록** (저장본 `data/sidebar_layout.json`이 이기므로 마이그레이션 필수)
- 집계 API: `GET /orders/api/settle-plan` (신규, 읽기 전용) — 서버 집계 후 JSON.
- 분류·버킷 엔진: 신규 모듈 `lemouton/margin/settle_plan.py` (가칭) — `_settlement_for`·`estimate_settle_from_history` 재사용, 자체 재계산 금지.
- 날짜 저장: `lemouton/markets/order_ingest.py` 각 `refresh_settlement*`에서 이미 파싱된 날짜를 `row['정산예정일']`로 저장(스윕 로직 무변경, 저장만 추가).
- 규칙표 저장소: `data/settle_plan_rules.json` (계정별 빠른정산 스위치 포함) + 조회/수정 라우트.
- 기존 화면(주문내역·마진계산기) 무변경. 폴백 SQLite면 스윕 저장 건너뛰기(기존 규약 동일).

## 7. 검증 계획

- pytest: 분류 4부류 상호배타(중복 0) 속성 테스트 · 쿠팡 분할 합=원금 · 버킷 경계(주=월~일) · 기한경과 분리 · 매출액 대체 카운트.
- 라이브: 실브라우저로 탭 진입 → KPI·표·드릴다운 실측, 마진계산기 정산합과 교차 대조(같은 원천이므로 총액 정합해야 함).

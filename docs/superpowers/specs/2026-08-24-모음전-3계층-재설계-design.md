## 0. 왜 이 작업을 하나

삼바(대량등록, 사장님의 다른 사업 — 실제 6마켓 등록이 매일 돌고 있는 프로그램)를 대조군 삼아

드러났다 — ① 22항목 중 13항목이 저장만 되고 마켓에 안 나간다(배선 문제) ② 정책 화면에 마켓마다

## 3. 데이터 모델 변경

### 3-1. 신규 테이블

🔴 **「안 정함」과 「0원」은 다르다** (2026-08-24 사장님 확정 — 구현 중 실측으로 잡음)
초안은 금액 칸을 `default=0, nullable=False` 로 뒀는데, 그러면 **아직 안 정한 계정**과
**0원(무료 반품)이라고 정한 계정**이 둘 다 `0` 으로 읽힌다. 배송비는 금전 직결이라 이
혼동이 곧 손실이다. 전 칸을 **NULL 허용**으로 바꿨다 — NULL = 안 정함, 0 = 0원.
기본값은 모델이 몰래 채우지 않고 `DEFAULT_FEES`(**반품 5,000 편도 · 교환 10,000 왕복**)를
**계정 설정 화면이 새 계정을 만들 때** 명시적으로 넣어 준다. 읽을 때는
`account_settings.value_of()`(값) 와 `is_set()`(정한 적 있나) 를 갈라 쓴다.

```python
# lemouton/policy/models.py 에 추가

class MarketAccountSetting(Base):
    """2층 — 계정마다 고정인 등록 설정. UploadAccount 1:1."""
    __tablename__ = 'market_account_settings'
    id = Column(Integer, primary_key=True)
    upload_account_id = Column(Integer, ForeignKey('upload_accounts.id'), unique=True, nullable=False)
    # 공통 컬럼(모든 마켓이 쓰는 것 — 오타 위험 큰 자주 쓰는 값만 컬럼으로 못박음)
    # 🔴 전부 nullable — NULL = 「아직 안 정함」, 0/'' = 「그렇게 정함」
    as_phone = Column(String(32))
    as_message = Column(Text)
    return_fee = Column(Integer)
    exchange_fee = Column(Integer)
    jeju_fee = Column(Integer)
    island_fee = Column(Integer)
    tax_type = Column(String(16))
    origin_default = Column(String(64))
    stock_default = Column(Integer)
    promotion_message = Column(String(200))
    # 마켓 전용 칸(옥션/G마켓 출고지번호, 롯데ON 배송정책번호 등) — 못박으면 마켓 늘 때마다
    # 마이그레이션이 필요해지므로 JSON. ★2 결정(JSON 한 칸)이 이 칸을 가리킴.
    extra = Column(JSON, default=dict)
    updated_at = Column(DateTime, default=_utcnow, onupdate=_utcnow, nullable=False)


class NameRule(Base):

class DetailTemplate(Base):

    __tablename__ = 'detail_templates'
    id = Column(Integer, primary_key=True)
    name = Column(String(120), nullable=False)
    top_html = Column(Text, default='')

    created_at = Column(DateTime, default=_utcnow, nullable=False)
    updated_at = Column(DateTime, default=_utcnow, onupdate=_utcnow, nullable=False)


class CategoryMappingReview(Base):
```

## 5. 마켓 API 연동 변경

### 5-1. 옵션별 이미지 마켓 지원 자동 판별 (§결정4)

```
스마트스토어 · 쿠팡 · 롯데ON : 옵션 이미지 받음 → 색상별 그대로 전송
11번가                        : 옵션 이미지 안 받음 → 대표 1장으로 자동 하향
```
`lemouton/registration/compile_*.py` 각 파일에 옵션 이미지 지원 여부 상수 추가, 없는 마켓은
`options[].image`를 대표 이미지로 덮어써서 보낸다(빈 값 전송 방지).

### 5-2. 즉시할인·쿠폰 3마켓 신규 연동 (§결정9)

| 마켓 | 방식 | 근거 API | 상태 |
|---|---|---|---|
| 옥션·G마켓 | 판매자할인 | 🔴 **별도 API 가 아니라 등록 payload 안**: `addtionalInfo.sellerDiscount` `{isUse, iac\|gmkt: {type, priceOrRate1, startDate, endDate}}` · 정액 최소 100원·10원 단위 · 정률 **70%까지** | ✅ 완료 2026-08-26 |
| 롯데ON | 판매자할인 저장 | 「판매자할인 저장」 apiNo=122 — 지도에 **[off]·상세 미접수**. URL 도 칸 이름도 없다 | **확인 불가** (지어내지 않음) |

🔴 착수 전 예상(「ESM `seller-discounts` 라는 별도 API」)은 **틀렸다.** 지도 전수정독으로
읽으니 등록 요청 안에 있었다 — 새 API 를 부르지 않고 기존 등록 payload 에 칸만 더하면 된다.

**주의**: 이 항목은 `consult-market-map` 스킬 게이트를 통과해야 코드를 만질 수 있다
(CLAUDE.md 판매처 API 규칙). Phase 착수 시 옥션·G마켓·롯데ON 세 마켓의 할인 API 브리핑을
`market_brief.py`로 먼저 전수정독한다.

### 5-3. 상품명 길이 — 쿠팡 예외 (§결정8 + ●확인)

`lemouton/registration/market_limits.py` 수정:
```python
NAME_MAX_LEN = {'coupang': 100, 'eleven11': 100}       # 기존 — 글자수, 그대로 유지
NAME_MAX_BYTES = {'eleven11': 99, 'lotteon': 149}       # 신규 — 삼바 실측 근거로 채움
```
검사 순서: 마켓에 `NAME_MAX_LEN`이 있으면 글자수로, `NAME_MAX_BYTES`가 있으면 바이트로,
**둘 다 있으면 먼저 걸리는 쪽**(11번가는 둘 다 있을 수 있음 — 100자 근거는 없었으므로 실제로는
바이트만 적용됨. 표는 향후 글자수 근거가 추가로 확보되는 마켓을 위해 구조를 겸용으로 둔다).

### 5-4. 쿠팡 brandId 미전송 버그 (§결정11 + ●확인)

`lemouton/registration/compile_coupang.py`에 브랜드 조회 단계 추가:
1. `BrandRegistryCache`에서 브랜드 조회 → 없으면 쿠팡 브랜드 검색 API 호출 → 캐시.
2. `matched=True`이면 `brandId`를 payload에 포함(현재 브랜드 이름 문자열만 보내는 부분에 추가).
3. `uid_required=True`이고 정품코드(GTIN/모델번호)가 없으면 **등록 보류**(§결정11 "모르면 막기"와
   같은 안전 원칙 — 소명 필요한데 코드가 없으면 거부당할 걸 미리 막는다).
4. `matched=False`(판정 불가)도 §결정11에 따라 막는다 — 사유를 화면에 그대로 노출.

## 7. 확인이 더 필요한 것 (미결)

1. ~~**옵션 갈래 §결정6**~~ — ✅ **2026-08-24 사장님 확정으로 방향이 바뀌었다.**

   설계서 §4-6 초안은 「색상×사이즈 표의 각 칸에 **재고를 손으로 입력**」이었는데,
   이는 CLAUDE.md 1번 규칙(「재고 기준 = 소싱처 실제 URL. 추정·폴백 금지」)과 부딪힌다.
   손으로 넣은 재고가 소싱 재고를 덮으면 없는 재고를 파는 오버셀이 난다.

   **사장님 확정**: 「기본적으로 소싱처 URL 의 재고를 따른다. 수기 입력은 **사입용**일
   때만이다(초기 재고로 갖고 있던 것, 또는 나중에 사입해서 추가한 것). **옵션에서 직접
   컨트롤하지 말고 재고관리에서 수량을 컨트롤**한다. 그 재고는 **사입용으로 구분**되어야
   하고, 수량은 **프로그램 전체에 반영**돼야 한다.」

   → 정책 화면에 재고 입력칸을 **만들지 않았다.** 대신 전송이 재고관리의 사입 수량을
     읽어 쓰도록 이었다(`to_payload._purchase_stock_by_sku`). 오버셀 막이 3중:
     소싱으로 팔 수 있으면 안 덮음 · 「있음(수량 미상)」도 안 덮음 · **소싱+사입 합산 금지**.
   → 「가짜 조합 자동 제외」는 여전히 스코프 밖이다(재고를 손으로 채우지 않으므로
     그 위험 자체가 줄었다).

   *(아래는 확정 전 기록)* — "가짜 조합 자동 제외"(소싱에 없는 색상×사이즈 조합을

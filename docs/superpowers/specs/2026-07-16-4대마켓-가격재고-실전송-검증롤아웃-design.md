## 1. 목적 (근본 목표)

소싱처/사입 제품의 **가격·재고 변동**을 크롤로 포착하고 **마진 가공**하여, 4대 판매처(**스마트스토어·쿠팡·롯데온·11번가**)에 **실제 업로드(실전송)**로 반영한다.

핵심 제약(프로젝트 CLAUDE.md): 가격·재고 오류 = 금전 손실 + 계정 리스크. 따라서 **마켓별로 "드라이런 숫자 = 실제 판매처 화면 100% 일치" 게이트를 통과해야만** 그 마켓의 실전송을 켠다. 폴백 금지·추측 금지·실패 표면화.

## 2. 현재 상태 (main 기준 실측)

**이미 완성·배선되어 있음** — 새로 만드는 게 아니라 "검증하고 마켓별로 개통"하는 일이다.

| 구성요소 | main 상태 | 위치 |
|---|---|---|
| 4단계 파이프라인 (A크롤→B마진→C포맷→D업로드) | ✅ 배선 | `scheduler/jobs.py`, `scheduler/main.py`(연속 사이클) |
| 마진 엔진(소싱/사입 분리) + 최종매입가 | ✅ 작동 | `lemouton/pricing/engine.py`, `pricing/final_price.py` |
| 포맷터(5마켓 페이로드 생성) | ✅ 작동 | `lemouton/formatter/pipeline.py` |

### 2.1 실전송 이중 잠금 (안전 핵심 — 변경하지 않음)

`real_upload_armed(session)` = 두 열쇠가 **둘 다** 켜져야 실제 어댑터, 아니면 `DryRunAdapter`.
- **서버 열쇠** `MOUM_LIVE_UPLOAD` (배포 env — 재배포로만 켬. 사용자가 직접).
- **화면 열쇠** `autosend_mode == 'real'` (자동화 설정 UI. 사용자가 직접).
- 설정 조회 실패 시 안전측(미전송).

### 2.2 마켓별 가격·재고 수정(update) 준비도 — 데이터 코드 지도 정본

| 마켓 | 가격 수정 | 재고 수정 | 지도 상태 | 실전송 경로 |
|---|---|---|---|---|
| 쿠팡 | 아이템별 가격 변경 | 아이템별 수량 변경 | 🟢 씀(실사용) | 즉시 가능 |
| 스마트스토어 | (v2) 원상품 수정 | 상품 옵션 재고 변경 | 🟢 씀(실사용) | 즉시 가능 |
| 롯데온 | 가격 API(apiNo=91·`prices.update_price`) | 재고 API(apiNo=86·`inventory.update_stock`) | 🟠 검증대기(코드 있음) | 검증 후 개통 |
| 옥션·G마켓(ESM) | 가격 수정(186) | 재고 수정(194)·옵션 full-replace(26) | 🟠 검증대기(코드 있음) | (이번 사이클 밖) |

색 범례: 🟢씀=우리 코드로 연결·실사용 / 🟠검증대기=코드는 있으나 실계정 검증 전 / 🔵안 씀=마켓 문서에만.

## 4. 아키텍처 — 검증 게이트 단계 롤아웃

전 과정 관통 안전 불변식:
- 이중 잠금 구조 **유지**. 마켓별로 최소 범위(1~2 옵션)부터 켠다.
- `price_guard`(0원·이상가·마진 하한·재고≤소싱재고) 상시 ON.
- **서버키 `MOUM_LIVE_UPLOAD` 설정·배포는 사용자가 직접.** 구현자는 준비·검증·런북까지.
- 실제 실전송 배치는 나가기 전 **매번 사용자 확인**(외부·비가역 행위).
- 정합성 기준 = **실브라우저 판매처 상품 URL/셀러 화면 실값**. 불일치 시 실전송 금지.

### Phase 0 — 토대
- fresh `main` 기반 작업 브랜치 확보.
- 실데이터로 파이프라인 한 바퀴 **드라이런 전수 검증**: 크롤 변동분(CrawlDelta) → 마진 → 5마켓 페이로드 → 드라이런 전송. 각 단계 산출 숫자를 대조.
- **Phase D 게이트 구멍 수정** + 회귀 테스트.

### Phase 1 — 스마트스토어·쿠팡 (🟢 검증완료 → 실전송)
- 드라이런 재확인(숫자 = 셀러 화면).
- 통제된 소량(1~2 옵션) 실전송 → 판매처에서 눈으로 확인 → 확대.
- 가격·재고 **양방향 라운드트립** 확인(올린 값이 판매처·재조회에서 동일).

### Phase 2 — 롯데온 (🟠 검증대기 → 검증 → 개통)
- 드라이런 숫자 vs 롯데온 셀러 화면 대조(가격 apiNo=91 / 재고 apiNo=86).
- 일치 확인 후 capabilities `verified` 승격(`markets/capabilities.py`).
- 소량 실전송 검증.

### Phase 3 — 11번가 (🔴 미확보 → 스펙 발굴 관문 → 구현 → 검증 → 실전송)
1. **스펙 발굴 관문(선행)** — 셀러 REST 가격·재고 수정 엔드포인트 경로 + 요청 XML 스키마 + 응답 성공/실패 코드를 **실제 셀러 API 응답으로 확정**(로그인 게이트 안. 콘솔 추출 단서 `prodmarketservice/prodmarket` 기점). 추측 금지 — 확보 못 하면 이 Phase는 보류.
2. `docs/markets/eleven11.yaml` endpoints/fields 채움 → 지도(map.html) 11번가 가격·재고 항목 갱신.
3. `shared/platforms/eleven11/prices.py`(`update_price`)·`inventory.py`(`update_stock`) 구현. **거짓성공 금지** — HTTP 200이라도 응답 result_code로 성공/실패 판정(11번가 발송처리 -3313 선례).
4. 드라이런 검증 → 소량 실전송.

## 5. 데이터 흐름 (실전송 경로)

```
크롤(로컬 PC) → SourceOption.current_price/stock upsert → CrawlDelta 변동분 기록
   ↓ (서버) scheduler full_cycle()
A: 변동분 로드 → B: run_pricing_engine(소싱/사입 마진, final_price) 
   → C: run_formatter(5마켓 페이로드) → D: run_uploader
      · real_upload_armed(): 서버키+화면키 둘 다 ON → 실제 어댑터 / 아니면 DryRunAdapter
      · price_guard: 0원·이상가 abort
      · pacer: 계정 단위 속도 제한
      · persist=live: 실제 전송 시에만 기준선 커밋(미전송분 오염 방지)
```

---

## 6. 에러 처리
- 마켓 API 실패 → `UploadResult.success=False` + DLQ(`uploader_dlq.jsonl`) 적재, 기준선 미커밋(재시도 가능).
- 거짓성공 금지: 응답 본문/코드로 실패 판정(11번가·롯데온 선례).
- price_guard abort는 실패로 표면화(조용한 실패 금지).
- 매칭 실패 옵션 → 폴백가 금지, 전송 대상에서 제외 + 알림.

## 7. 테스트 전략
- Phase 0: 파이프라인 드라이런 골든 스냅샷(실데이터 표본) 대조 + Phase D 게이트 회귀 테스트(롯데온/ESM 단독 변동이 드롭되지 않음).
- 이중잠금: 기존 `test_two_key_gate.py` 확장(마켓별 arm 여부).
- 롯데온: 드라이런 페이로드 = 셀러 화면 골든 대조.
- 11번가: 어댑터 성공/실패 판정 테스트(모의 응답 코드별) — 거짓성공 회귀 방지.
- 실전송 검증은 **실브라우저 셀러 화면 대조**로 마무리(코드 테스트로 대체 불가).

- 옥션·G마켓(ESM) 실전송 — 검증대기 상태이나 이번 4대 마켓에서 제외(별도 사이클).

## 9. 분해 (구현 플랜 순서)
스펙은 4대 마켓을 한 흐름으로 담되, 구현 플랜은 **Phase 0 → 1 → 2 → 3** 순차. Phase 3(11번가)은 스펙 발굴 관문 때문에 사실상 자체 사이클 — 확보 실패 시 Phase 0~2만으로 사이클 종료 가능(11번가는 후속).

## 10. 완료 기준
- Phase 0~2: 실데이터 드라이런 전수 일치 + 스마트스토어·쿠팡·롯데온 소량 실전송이 실제 판매처 화면에 정확히 반영됨(라이브 검증).
- Phase 3: 11번가 스펙 확보 시 구현·검증·소량 실전송까지. 미확보 시 관문에서 명시적 보류(거짓 완료 금지).
- 전 과정 이중 잠금·price_guard 무력화 없음. 서버키는 사용자가 켬.

# 크롤 속도 향상 + 변동분(delta) 피드 — 설계

> **계층**: 스펙 (설계 단일 진실 원천)
> **책임**: 크롤 속도 향상 3축(소싱처별·동시성·변동분) + 로컬 검증 게이트 설계
> **상위 의존**: 프로젝트 CLAUDE.md (🔒 데이터 정합성 3대 원칙), `docs/크롤링-가이드.md`
> **관련 코드**: `프로그램/_시스템/extension/moum-crawler/background.js` (크롤 엔진)
> **작성일**: 2026-07-07

## 0. 목표와 제약

### 사용자가 정한 것
- **1순위 = 안정성 유지.** 지금의 안정장치(타임아웃·재시도·증분저장·자원가드)를 회귀 없이 보존.
- **진짜 목표 = "변한 것만" 반영 + 변동분을 따로 알기.** 전량을 빨리가 아니라, **재고·가격 변동분**을 저비용으로 잡고 그 delta를 표면화.
- **가시성 = 평소 숨김 + 원할 때 감시 토글.** 창을 눈으로 보는 원칙은 옵션으로 격하.
- **PC = 고사양이나 크롤 중에도 사용.** 상한은 올리되 자원 가드는 유지.
- **배포 조건 = 로컬에서 완벽히 검증되기 전엔 배포 없음.** 소싱처 단위로 통과한 것만 켠다.

### 절대 제약 (🔒 CLAUDE.md 3대 원칙 — 예외 없음)
1. 재고·가격 기준 = 소싱처 **실브라우저 상품 URL**의 실제 값. 추측·폴백·평균 금지. 확인 못 하면 "확인 불가".
2. 크롤 = **로컬 PC**(크롬 확장). 서버 크롤 부활 금지. 본 설계의 "창 없는 fetch"도 **로컬 확장 서비스워커 안**에서 돈다 — 서버 아님.
3. 매칭·크롤 실패 시 대표가 폴백 금지 → "가격 없음 + 크롤 실패" 표면화.

## 1. 현재 엔진 구조 (기준선)

`background.js` 크롤 엔진(멀티 모음전 큐 + 적응형 동시성):

- **모델**: "소싱처 1곳당 창 1개" → 그 창(탭 1개)에서 URL을 **한 개씩 순차** 이동(navGrab/navExtract)하며 크롤. (`runSource`, background.js:1236~)
- **동시성 = 병렬로 도는 *소싱처 창* 개수.** `cap = clamp(hardwareConcurrency − 1, 1, 3)` → **최대 3**. 1에서 시작, 처리량·CPU·MEM 보고 ±1 적응. (`evaluateConcurrency`, background.js:1222·1343)
- **안정장치(보존 대상)**:
  - 유닛 하드 타임아웃 `UNIT_TIMEOUT_MS = 60000` (background.js:466, `withTimeout`)
  - 실패 1회 즉시 재시도(같은 창) + 부하 낮은 시점 **최종 재시도 패스**(신규 창) (background.js:1294·1385)
  - 소싱처 완료 즉시 **증분 저장**(`saveItemsBG`) (background.js:1321)
  - 자원 한계(CPU≥95·MEM≥98) 강제 −1, 정직성 게이트(0건인데 완료 위장 방지) (background.js:1349·1332)

### 두 개의 병목 (분리)
- **가로 병목** = 소싱처 창 최대 3개.
- **세로 병목** = 한 소싱처 안에서 URL을 **1개씩** 처리. URL이 몰린 소싱처에서 이쪽이 더 크다.
- 렌더 페이지 1건 = 이동+로드+하이드레이션+안정화대기 ≈ **3~8초**. JSON 직접 fetch ≈ **0.2~1초**.

## 2. 전체 전략 = C(단계적), 검증 게이트를 backbone으로

속도의 최대 지렛대는 창 개수가 아니라 **①변한 것만 크롤 ②API 소싱처는 창 없이 병렬 fetch**. 둘 다 *일을 덜 해서* 빨라지므로 안정성과 충돌하지 않는다.

- **1단계(저위험 즉효)**: 창 없는 fetch 빠른 길 + 상한 상향 + 소싱처 내 병렬.
- **2단계(진짜 목표)**: 스냅샷 + 변동분 피드 + "변한 것만" 모드.
- 각 단계는 **독립적으로 로컬 검증→배포**. 한 번에 밀어붙이지 않음.

## 3. 검증 게이트 (배포 전 필수 — 사용자 못 박음)

모든 변경은 **feature flag OFF 기본**으로 들어가고, 아래를 로컬에서 통과해야만 켠다.

| # | 게이트 | 통과 기준 |
|---|--------|-----------|
| G1 | **소싱처별 값 100% 대조** | 새 fetch 경로 값이 그 소싱처 실브라우저 URL 값과 완전 일치(샘플 URL 전수). 재고 3상태·표면가·최종매입가 모두. |
| G2 | **구·신 결과 diff = 0** | 같은 모음전을 옛 방식/새 방식 둘 다 돌려 결과 나란히 비교. 설명 안 되는 차이 0건. |
| G3 | **안정장치 회귀 0** | 타임아웃·재시도·증분저장·자원가드 동작 유지 확인. |
| G4 | **소싱처 단위 ON** | 통과한 소싱처만 플래그 ON. 실패 소싱처는 기존 창 크롤 유지. 폴백·추측 없음. |

- 플래그 예: `FAST_FETCH_SOURCES`(콤마구분 소싱처키), `CRAWL_CONCURRENCY_CAP`(정수), `DELTA_FEED_ENABLED`(bool).
- 로컬 검증은 `/live-browser-verify` + `/ui-verify` 절차를 따른다.

## 4. 1단계 설계 — 안전한 속도

### 2-1. 소싱처별 — 창 없는 fetch 빠른 길
- **대상 확정 절차**: 소싱처마다 "재고·가격이 (a) JSON API 응답 또는 (b) 초기 HTML `__PRELOADED_STATE__` 에 있는가"를 조사.
  - **API형(무신사 goodsPrice API·롯데온 API·네이버 SKU API)**: 창 없이 확장 서비스워커에서 직접 `fetch` → 파싱. 창·탭·렌더·하이드레이션 전부 생략.
  - **렌더형(르무통·SSF·SSG·스스)**: 초기 HTML에 값이 있으면 fetch 경로 가능. JS로 뒤늦게 그려지면 **창 크롤 유지**(fetch 불가로 판정).
- **구조**: 소싱처별 `fetchPath` 함수(있으면) ↔ 기존 `runSource`(창) 를 **플래그로 분기**. fetchPath 실패 시 자동으로 창 크롤로 폴백(값 폴백 아님 — *경로* 폴백).
- **병렬**: fetch 경로는 창이 없으므로 소싱처 안 URL을 **동시 fetch**(동시성 별도 상한, 예 6~10). 소싱처의 서버 부하를 고려해 소싱처별 상한 설정.
- **게이트**: G1(값 100% 대조) 통과 소싱처만 fetch 경로 ON.

### 2-2. 동시성 / 메모리 — 상한 상향 + 소싱처 내 병렬
- **상한 상향**: `cap` 계산의 하드 클램프 `3` → 설정값(`CRAWL_CONCURRENCY_CAP`, 기본 예 6). 창을 숨길 수 있어 "눈으로 봄" 제약이 사라졌으므로 가능.
- **자원 가드 유지(필수)**: `evaluateConcurrency`의 CPU≥95·MEM≥98 강제 −1, CPU≥90·MEM≥96 상향 보류 로직 **그대로**. 크롤 중 PC 사용 대비.
- **소싱처 내 병렬**: 창 크롤이 남는 렌더형 소싱처도, 한 창에서 1개씩 대신 **탭 N개 동시 이동**(또는 창 N개)으로 세로 병목 완화. 탭 수는 자원 가드에 연동.
- **가시성 토글**: 창 생성은 기본 숨김/최소화, "감시" 토글 시 표시. (구현 시 UI = `/design-mockup` 게이트 대상)

## 5. 2단계 설계 — 변동분(delta) 피드

### ★ 데이터 모델 — 새로 만들지 않는다 (기존 `PriceTrackHistory` 재사용)
데이터지도 숙지 결과: **가격·재고 변동은 이미 `PriceTrackHistory`에 시계열로 쌓이고 있다.**
- `lemouton/templates/models.py:140` — `price`, **`stock`**, `source_option_id`, `captured_at` 컬럼. 매 크롤 append. (`/track` 탭·홈 "24h 가격변동" KPI가 이걸 읽음)
- 따라서 **변동분 = `PriceTrackHistory`의 옵션별 최신 2행 diff**(price·stock). 신규 `CrawlSnapshot`/`CrawlDelta` 모델을 만들면 단일 진실 원천(④) 위반 → **만들지 않는다.**
- 필요한 건 "diff를 뽑아 보여주는 조회/뷰"뿐. 이벤트성 리치 의미(예: 자동화 트리거)가 정말 필요할 때만 `ChannelChangeEvent`(자동화 로그, 기존) 재사용 검토.
- ⚠️ 선행 검증: `PriceTrackHistory` append가 **일반 확장 크롤 저장 경로에서도 실제로 일어나는지** 확인(현재 `bulk_crawl.py`·스크립트 경로는 확실, 메인 `save_crawl_result` 경로는 플랜에서 확인).

### 변동분 피드 (UI — 별도 `/design-mockup` 게이트)
- "오늘 뭐가 변했나": 품절↔재입고, 가격 변경 목록. 소싱처·모음전별 필터.

### "변한 것만" 모드 (선택적, 최대 절감)
- **싼 확인 → 다르면 그것만 깊게**. 핵심: 건너뛰기는 **추측이 아니라 저비용 실제 확인** 근거여야 🔒원칙 위반이 아님.
  - 우선순위: (a) 소싱처 서버의 조건부 요청(ETag/Last-Modified) 304 = 권위 있는 "안 변함" → 스킵 가능. (b) 저비용 fetch로 현재값 읽어 비교(이미 읽었으니 stale 아님). (c) 둘 다 불가면 그냥 깊게 크롤.
  - **절대 금지**: "last_crawled_at 최근이니 안 변했겠지" 식 시간 기반 추측 스킵(= stale을 진실로 → 위반).

## 6. 컴포넌트 경계 (독립 검증 단위)

| 단위 | 하는 일 | 의존 | 검증 |
|------|---------|------|------|
| `sourceFetchPath[sk]` | 소싱처별 창 없는 fetch·파싱 | 소싱처 API/HTML | G1 값 대조 |
| 경로 분기기 | fetchPath ↔ 창 크롤 플래그 분기 + 경로 폴백 | 플래그 | G2 diff |
| 동시성 컨트롤러(확장) | cap 상한·자원가드·소싱처 내 병렬 | sysinfo | G3 회귀 |
| 스냅샷/델타 저장 | 스냅샷 보관 + diff → CrawlDelta | DB | 단위 테스트 |
| 변동분 피드 UI | delta 표시 | CrawlDelta | design-mockup + ui-verify |

## 7. 롤아웃 순서

1. **1단계-2-1**: fetch 경로를 소싱처 1곳(예 무신사)만 구현 → G1·G2·G3 로컬 통과 → 그 소싱처만 ON → 배포. 이후 소싱처 하나씩 확장.
2. **1단계-2-2**: 상한 상향 + 소싱처 내 병렬 → 로컬 부하·안정 검증 → 배포.
3. **2단계**: 스냅샷/델타 모델 → 변동분 피드(UI 게이트) → "변한 것만" 모드(선택).

각 항목 **끄기 기본 → 로컬 검증 → 소싱처/기능 단위 ON → 배포**. 워크트리 작업 시 master 머지 + 라이브 재시작까지 완료(글로벌 원칙 6).

## 8. YAGNI / 범위 밖 (지금 안 함)
- 서버 크롤(원칙 위반), 시간 기반 추측 스킵(원칙 위반).
- 소싱처 API 리버스엔지니어링이 과한 곳은 fetch 경로 포기하고 창 크롤 유지 — 억지로 전 소싱처 fetch화 안 함.
- 변동분 알림(Telegram 등)은 후속. 지금은 피드 화면까지.
- 신규 스냅샷/델타 모델(위 5장 참조 — 기존 `PriceTrackHistory` 재사용).

## 9. 데이터지도 7탭 숙지 — 설계에 박히는 제약

정본 = 인앱 **데이터 흐름 지도**(`sourcing_guide/data_flow_doc.html`, TOC 7절). 각 절이 이 설계에 거는 제약:

| # | 절 | 이 설계에 주는 제약 |
|---|-----|---------------------|
| 1 | 전체 그림(4단계) | 수집→가공→전송을 자동화 스케줄러 `full_cycle`이 60초 반복. 속도 개선은 **수집 단계만** 건드림. 가공·전송 불변. |
| 2 | ① 수집 | 두 경로: **BG_PARSE_SOURCES**(확장 HTML 수집→`POST /api/sources/parse` 서버 파서, 르무통·SSF·SSG…) / **BG_JS_SOURCES**(확장 직접 추출→`POST /api/sources/crawl-result`, 무신사·롯데온). **수집=로컬(확장), 파싱만 서버.** 새 fetch 경로도 이 두 엔드포인트로 합류(별도 저장 경로 신설 금지). |
| 3 | ② 가공 | 저장=`SourceProduct.last_price`·`SourceOption.current_stock`·`dynamic_benefits_json`. 계산=`compute_market_price`. **fetch 경로가 뽑은 값도 반드시 이 저장/계산으로 흘러야** 매트릭스·재고관리·track이 일관. |
| 4 | ③ 전송 | 업로드는 `LEMOUTON_LIVE_UPLOAD` OFF(드라이런). 본 작업 범위 밖 — 건드리지 않음. |
| 5 | ④ 공유 원천(SSOT) | 표면가·최종매입가·`window.DATA`는 **한 곳에서만** 산출. → 변동분·fetch 경로 모두 **읽기/합류만**, 병렬 원천 신설 금지. |
| 6 | ⑤ 탭별 데이터 지도 | 변동분 표면화 후보 지점: 홈 "24h 가격변동" KPI(`PriceTrackHistory`), `/track` 탭, `/audit`(before/after). **변동분 피드는 이들과 같은 원천을 써야 함.** |
| 7 | 검증 현황 | 이 지도는 **코드 근거 검증**만 됨(라이브 가격·재고 검증 아님). → 본 설계의 G1·G2는 그 위에 **실브라우저 값 검증**을 더한다. |

## 10. 소싱처별 창없음(fetch) 실현 가능성 — 탭2 방식표 근거

탭2(재고)의 소싱처별 수집 방식에서 도출. **fetch 경로 = 창(navGrab/navExtract) 없이 확장이 raw 응답만 받아 기존 저장 경로(`/api/sources/parse` 또는 `/crawl-result`)로 합류.**

| 소싱처 | 재고 수집 방식 | 창없음 fetch | 근거·주의 |
|---|---|---|---|
| 무신사 | **API** (prioritized-inventories) | ✅ 유력 | 옵션별 실수량 JSON. 표면가도 API(salePrice). 혜택만 로그인. |
| 롯데온 | **API** (option/mapping stkQty) +DOM | ✅ 유력 | stkQty 실수량. DOM은 폴백. |
| 르무통 | **내장JSON** (option_stock_data) | ✅ 유력 | Cafe24가 실판매조합·실재고를 HTML에 통째 박음. 무로그인. |
| SSG | **내장JSON** (uitemObj usablInvQty) | ✅ 유력 | 익명 curl_cffi 서버 접근 가능. SSR HTML JS블록. |
| 스마트스토어 | **API** (per-SKU stockQuantity) | ⚠️ 조건부 | WAF가 서버 직접호출 차단 → **로그인 확장 세션**에서만 fetch 가능. A.id 사용(productNo면 999 둔갑). |
| 롯데아이몰 | 내장JSON (itemInvQtyInfo) | ⚠️ 검증 | **WAF 403** → curl_cffi 위장 또는 navGrab. plain fetch 통과 여부 G1에서 확인. |
| 현대H몰 | 내장JSON (__NEXT_DATA__) | ⚠️ 검증 | 전용 API는 **방화벽 차단**→navGrab. 페이지 HTML의 __NEXT_DATA__를 plain fetch로 받는지 G1 확인. sellGbcd 우선 판정 필수. |
| SSF | **DOM/정규식** (statcd, lazy 렌더) | ❌ 창 유지 | 옵션이 `<script>` JS문자열, **콜드 창서 빈 결과**(background.js:338). 렌더 필요 → 기존 창 크롤 유지. |

- ✅ 유력 4곳(무신사·롯데온·르무통·SSG)부터 G1 대조 → 통과 시 fetch 경로 ON. 1단계 첫 대상.
- ⚠️ 3곳은 WAF/방화벽 통과 여부를 G1에서 실측 후 판단(폴백 금지 — 안 되면 창 유지).
- ❌ SSF는 처음부터 창 유지(fetch 시도 안 함).

## 11. §7 동기화 의무 (탭7)

크롤 코드를 바꾸면 **같은 작업에서 정본도 갱신**해야 함(어긋나면 잘못된 설명서):

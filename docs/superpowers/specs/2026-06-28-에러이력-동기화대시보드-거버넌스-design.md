## 1. 배경 · 문제

`§5 에러 이력` 카탈로그(현재 55건)는 양식(2축 분류·근본원인·재발방지·커밋)은 잘 갖춰졌으나 **세 가지가 빠져 있다**:

1. **거버넌스 부재** — 새 에러를 추가할 때 중복(같은 원인 재기재)·모순(§1~4와 어긋남)을 막는 명문 규칙이 없다. 세션이 바뀌면 같은 걸 새 번호로 또 적을 위험이 실재한다.
2. **반영 여부 불가시** — 어떤 재발방지가 **실제 크롤 코드에 들어갔는지** 한눈에 안 보인다. 원문(.md)·보기(map.html EC 배열)·실제 코드가 서로 어긋나도 표면화되지 않는다.
3. **이력 부재** — 각 에러가 언제 추가/수정/삭제됐는지(rev) 기록이 없다.
4. **교차 회귀 위험** — 같은 근본·같은 코드를 여러 소싱처가 공유한다(예: S1·S2·S8 모두 옵션행 미생성). 한 소싱처 고치려고 **공유 코드를 건드리면 다른 소싱처가 깨진다**(실제 `94466889` stale 머지가 2단계 매칭을 되돌려 재고매칭 광역 회귀). 어느 코드를 누가 공유하는지 안 보인다.

## 2. 핵심 개념 — 전체크롤이 기준, 원문·보기는 후행

진실의 순서를 못박는다:

```
전체크롤(코드) ──기준(SSOT)──▶ 원문(.md) ──후행──▶ 보기(map.html EC)
```

- **전체크롤(코드)** = 판정 기준. 재발방지가 실제 코드에 있나가 진실.
- **원문·보기** = 그 코드를 따라왔나(후행)만 본다. 독립 ✅/❌가 아니라 `동기화 / 뒤처짐`.

→ 경보가 **딱 두 종류**로 정리된다:
- **❌ 코드 미반영** = 전체크롤 ✕ (재발방지가 코드에 없음) = 버그 미해결, 진짜 손볼 곳.
- **🔄 문서 뒤처짐** = 전체크롤 ✓ 인데 원문/보기가 후행 안 됨 = 가이드만 갱신하면 끝.
- (그 외 = ✅ 완전 동기화)

## 3. 데이터 모델 — 기존 분류 유지 + 신규 필드

분류·컬럼은 **기존 카탈로그 그대로**(F계열 같은 새 추상 도입 ❌). `map.html`의 `EC[]` 배열 항목 스키마를 확장한다:

| 필드 | 기존/신규 | 의미 |
|---|---|---|
| `g` | 기존 | 크롤 영역 — `재고가격`(📦+💰 재고×가격) · `재고`(📦) · `가격`(💰) · `기타`(🛠️) |
| `l` · `l2` | 기존 | 수정(계층) — `be`(백엔드) · `fe`(프론트) · `etc`(기타) |
| `src` | 기존 | 소싱처 |
| `st` | 기존 | 수정 상태 — `ok`(수정됨) · `todo`(미수정) |
| `sy` | 기존 | 내용(증상) |
| `cz` | 기존 | 원인 |
| `pv` | 기존 | 재발방지 |
| `cm` | 기존 | 커밋 |
| **`code`** | **신규** | `{ sym: "파일:함수", desc: "한 줄 설명" }` — 재발방지가 박힌 **코드 앵커**. 화면에 항상 표시. |
| **`crawl`** | **신규** | 전체크롤 반영 — `ok`(반영) · `no`(없음) · `warn`(심볼만, 라이브검증 필요). **`code.sym` 자동 심볼검사로 도출**(§5). |
| **`doc`** | **신규** | 원문 동기화 — `sync` · `lag`. |
| **`view`** | **신규** | 보기 동기화 — `sync` · `lag`. |
| **`rev`** | **신규** | `[{ d, a, txt, src, cm }]` — 변경 이력. `a` = `add`·`mod`·`del`. |
| **`scope`** | **신규** | 수정 범위 — `source`(소싱처 전용 코드, 타 소싱처 무영향) · `shared`(공유 코드, 여러 소싱처 영향). **같은 `code.sym`을 2+ 소싱처가 쓰면 자동 `shared`.** |

**섹션 분류(파생)**: `코드미반영 = crawl==='no'` / `문서뒤처짐 = crawl!=='no' && (doc==='lag' || view==='lag')` / `완전동기화 = 그 외`.

**공유 코드 영향맵(파생)**: 모든 항목을 `code.sym` 기준으로 클러스터링 → 같은 심볼을 쓰는 항목들이 "함께 영향받는 소싱처" 집합. `scope`·회귀 대상·대시보드 공유 태그의 단일 근거. 예: `_match_option_so`(전 소싱처), `persist_crawled_options`(르무통·스스·무신사), `compute_breakdown`(가격 다수).

## 4. 화면 — 동기화 대시보드 (확정본 v7)

`바탕화면/모음전 에러이력 미니멀 확정본 v7.html` 기준. 미니멀(흰 배경·가는 선·최소 색).

- **요약 한 줄**: 총 / 완전 동기화 / 문서 뒤처짐 / 코드 미반영.
- **상태별 3섹션**(얇은 색 점 헤더): 코드 미반영 → 문서 뒤처짐 → 완전 동기화(접어둠). 어긋난 것이 위로.
- **각 섹션 = 컴팩트 표**: `영역 · 수정 · 소싱처 · 내용·코드 · 크롤 · 원문 · 보기`. 한 줄에 다, 어긋난 칸이 `✕`(빨강)·`△`(노랑)으로 즉시.
- **내용 아래 코드 한 줄**: `⚙ 심볼 확인/미발견` + `파일:함수 — 설명` + **공유 태그**(`🔗 공유 · 르무통·스스·무신사` 또는 `단독`). 공유 태그는 `code.sym` 클러스터에서 자동.
- **행 클릭 → 펼침**: 원인 · 재발방지 · 모순 사유(있으면) · **공유 코드면 "함께 영향받는 소싱처 N건 — 수정 시 회귀 재크롤 필수"** · rev(날짜·액션·내용·소싱처·커밋).
- **위치**: `§5 에러이력`의 첫 화면(보기 탭). 기존 사건표(영역별)는 그 아래 유지.

## 5. 자동 점검 — `guide_sync.py` 확장 (기계로 가능한 것만)

신규 순수함수로 **구조 무결성 + 심볼 존재**를 검사하고, 위반 시 가이드 상단 배너로 표면화. 의미 판단(진짜 중복인가·§1~4와 모순인가)은 기계가 못 하므로 **§6 규약이 사람에게 강제**.

자동 검사 항목:
1. **심볼 존재검사** → `crawl` 판정 근거. 각 항목 `code.sym`의 함수/심볼을 repo 코드에서 grep. 있으면 후보 `ok`, 없으면 `no`.
   - ⚠️ **한계**: repo만 검사. **라이브 데스크톱 확장(v0.7.x)은 stale repo 사본(v0.4.x)과 달라** 확장 측 심볼은 라이브 미검(기지 한계, [[reference_loaded_extension_path]]). 확장 항목은 `warn`로 표기.
   - ⚠️ 심볼 존재 ≠ 의미상 정상. grep-found는 엄밀히 `warn`(심볼만)이며, 라이브 재크롤 검증 후 사람이 `ok`로 승격. 기본은 found→`ok`로 두되 검증 필요 항목만 `warn`.
2. 사건 **ID 유일성**(중복 번호 탐지).
3. 상태값 enum(`st`·`crawl`·`doc`·`view`·`a`)만 허용.
4. **원문(.md)↔보기(EC 배열) 일치** — 건수·소싱처 키가 양쪽에 다 있나(드리프트 0).
5. §4 원칙표가 가리키는 사건 ID 실재.
6. **심볼 클러스터링(공유 코드 영향맵)** — 같은 `code.sym`을 쓰는 항목이 2+ 소싱처면 `scope=shared` 자동 + 함께 영향받는 소싱처 나열. 공유 코드 수정 시 회귀 대상이 자동 노출(거버넌스 §6 회귀 의무의 근거). ⚠️ "그 커밋이 어느 심볼을 건드렸나"의 자동 매칭은 어려우므로, 회귀 검증 강제는 §6 규약(사람)이 담당.

## 6. 기재 거버넌스 — 추가/수정/삭제 판정 (중복·모순 방지)

새 에러를 만나면 **확인 → 추가/수정/삭제 중 하나**. §5 머리에 박스로 명문화하고, CLAUDE.md 훅이 "크롤 작업 전 §5부터 읽어라"로 강제(이미 존재).

**STEP 1. 근본원인 규명** — 증상 아닌 "왜"를 먼저 확정(없으면 분류 불가).

**STEP 2. 추가 vs 수정 판정**
- 같은 `소싱처 + 같은 근본원인 + 같은 증상`이 이미 있나? → **있으면 ✏️ 수정**(기존 행에 커밋·날짜·rev 보강), 새 행 금지.
- 없으면 → **➕ 추가**(새 행 + ID). 단 같은 근본이 다른 소싱처면 둘 다 남김(히스토리 보존, 예: S1·S2·S8).

**STEP 3. 모순 검사** — 새 재발방지가 §1~§4와 어긋나나?
- (a) §1~4가 틀림 → §1~4 정정.
- (b) 코드가 §1~4 위반 중 → 사건으로 적되 본문에 **"§X 위반 중" 명시**(S14·S16 방식).
- (c) 둘 다 아닌데 모순 → **사용자에게 보고**(자동 덮어쓰기 금지).

**STEP 4. 수정 범위 — 소싱처 한정 우선 · 공유 코드 회귀 (교차 회귀 방지)** ⭐
한 소싱처 문제를 고칠 때, 어디를 고치느냐로 갈린다:
- **소싱처 한정(`scope=source`) 우선** — 소싱처 전용 코드(예: `lotteon.py:_realSpd`, `musinsa.js:buildInvMap`)에서 고칠 수 있으면 거기서. 타 소싱처 무영향. **가능하면 항상 이쪽.**
- **공유 코드(`scope=shared`) 불가피할 때** — 근본이 진짜 공유 코드(예: `_match_option_so`, `persist_crawled_options`, `compute_breakdown`)면:
  1. 그 `code.sym`을 쓰는 **다른 소싱처 에러 전부를 회귀 대상으로 식별**(공유 코드 영향맵, §3).
  2. 그 소싱처들 **재크롤 검증** + 각각 `rev` 기록. 검증 전엔 영향 소싱처 `crawl`을 **`warn`(검증필요)으로 강등**(섣불리 ✓ 금지).
  3. 회귀 테스트(예: `test_stock_matching`)가 있으면 PASS 확인.
- **금지** — "이 소싱처만 보고" 공유 코드를 바꿔놓고 다른 소싱처 미검증(= `94466889` 회귀 재발). **공유 코드 수정 = 다항목 변경**으로 취급.

**STEP 5. 삭제** — 버그 아님 판명 또는 진짜 중복일 때만 🗑️. 같은 근본으로 묶을 수 있으면 삭제 말고 유지(무결성).

**STEP 6. ID·rev** — prefix(S재고/P가격/O기타)+다음 일련번호(재사용 금지). 추가/수정/삭제 시 `rev` 한 줄 누적(날짜·액션·내용·소싱처·커밋). 공유 코드 수정이면 영향 소싱처 항목들에도 rev 동반. ⏳면 빠른복귀 인덱스에도 등재.

**STEP 7. 양쪽 반영** — 원문(.md) + 보기(EC 배열) **둘 다** 갱신. §5 자동점검이 건수 불일치를 잡음.

## 7. 비목표 (YAGNI)

- F계열/패턴 카탈로그 같은 **추상 일반화 레이어 도입 안 함**(사용자 결정 — 기존 분류 유지).
- 라이브 확장(v0.7.x) 측 심볼의 라이브 자동검사는 범위 밖(repo 한계 명시로 갈음).
- rev 의 코드 자동 추출(커밋 후크 등) 안 함 — 기재 시 수동 한 줄.

## 8. 구현 범위 요약

1. `map.html` `EC[]` 스키마 확장(`code`·`crawl`·`doc`·`view`·`rev`·`scope`) + 동기화 대시보드 렌더(상태별 3섹션 컴팩트 표 + 펼침 + 공유 태그). v7 마크업 이식.
2. 55건에 신규 필드 1회 채움(코드 앵커·crawl/doc/view·기존 rev 역산·`code.sym` 클러스터로 `scope` 도출).
3. `guide_sync.py`에 §5 검사 추가(심볼 존재·ID 유일·enum·원문↔보기 일치·**심볼 클러스터→공유 영향맵**) + 배너.
4. 원문 `크롤링-가이드.md` §5 머리에 **기재 거버넌스 박스**(§6, 교차 회귀 방지 STEP 4 포함) + 동기화 개념(§2) 추가.
5. (배포) origin/main 워크트리 분기 → push main → AWS. 라이브 검증.

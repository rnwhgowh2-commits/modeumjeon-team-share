# 판매처(마켓)별 API 단일 진실 원천 — 설계 문서

> **계층**: 프로젝트 스펙 (docs/superpowers/specs)
> **책임**: 6개 판매처 마켓의 **모든 API 코드·구분자·필드**를 한 곳에 담는 참조 문서 체계 설계
> **상위 의존**: 프로젝트 CLAUDE.md (데이터 무결성·중복금지)
> **작성일**: 2026-07-16
> **관련 기존 산출물**: `docs/markets/_schema.yaml`(구 스키마·이 문서로 대체), `docs/markets/{coupang,smartstore}.yaml`(→ .md 이관), 인앱 「데이터코드 지도」 `webapp/templates/marketplace_guide/map.html`(사용자용 화면·중복 아님)

---

## 1. 목적 (왜) — 반복 노가다 종식

**실제 겪는 문제**: 새 기능을 추가할 때 "데이터코드 지도 봐" 라고 해도, 지도가 **얕아서**(엔드포인트 이름 + apiNo 만 있고 **실제 요청 파라미터·응답 JSON 이 없음**) Claude 가 구현을 못 한다. 결국 사용자가 **매번** 공식 API 문서로 돌아가 F12 콘솔로 실제 요청/응답을 캡처·복붙한다 → **동일한 중복 노동 무한 반복**.

**해결 원칙**: 문서에 **"다시 볼 것"을 남기지 않는다.** 각 API 마다 **실제 요청 + 실제 응답 JSON 통째 + 필드별 뜻**까지 박아넣어, 그 문서만 보면 F12 재방문이 불필요하게.

> 앞으로 사용자는 **"이 기능 추가해줘"** 라고만 말하고, Claude 는 **원본 API 문서·F12 없이 이 문서만 읽어** 구현한다.

**역할 분담** (한 API 당 1회):
- **사용자** = 원본 그대로 **노가다 붙여넣기** (F12 응답 JSON·공식 문서 캡처·복붙 — 가공 불필요).
- **Claude** = 붙여넣은 원본을 **구조화·문서화** (표·필드 뜻·성공판정 정리).

핵심 요구 4가지:
1. **완전성(深)** — 작업이 있다는 사실뿐 아니라 **실제 요청 파라미터 + 실제 응답 JSON 전체 + 필드별 뜻**까지. 이게 F12 를 없애는 실질.
2. **커버리지(廣)** — 가격·재고·등록·주문조회·상태전환·송장·클레임·정산·CS 전 작업.
3. **뜻 보존** — 모든 코드/구분자·응답 필드에 **평문 뜻**(미래의 Claude 가 `-3313`·`odPrgsStepCd` 가 뭔지 모르면 안 됨).
4. **무결성** — 진실 원천 **1곳**. 손으로 관리하는 사본 금지.

형식은 **표 + 원본 JSON 블록을 함께 품는** 마크다운 — 표는 Claude·사용자 둘 다 읽고, ```json 블록```은 F12 원본을 손실 없이 그대로 보관한다.

## 2. 형식 결정 (표 중심 마크다운, 확정)

- `docs/markets/*.yaml` 은 **어떤 코드도 import 하지 않음**(grep 확인). 즉 런타임 설정이 아니라 순수 참조 문서 → YAML의 "기계가 읽음" 장점이 무의미.
- 마크다운 표는 사람이 읽기 편하고 Claude 도 완벽히 파싱 → **표 중심 마크다운 채택**.
- 서술형 문장의 애매함은 **고정 컬럼 표**로 채워 제거.

## 4. 마켓 파일 1개 = 표 7종(+ 식별자 지도 3b) + 작업별 상세 블록

각 `docs/markets/{market}.md` 는 아래 표를 순서대로 담는다. 표3b(식별자 지도)는 표3의 동반 표다. **보완점 6가지가 표 컬럼/블록으로 흡수됨.**

### 표1. 메타
| 항목 | 값 |
|---|---|
| 마켓키 / 표시명 | `coupang` / 쿠팡 |
| base_url | `https://api-gateway.coupang.com` |
| 인증방식 | HMAC-SHA256 (CEA) |
| 최종검토일 | 2026-07-16 |
| 근거 | 코드 추출 + (사용자 제공 API 문서) |

### 표2. 인증 · 계정 (← 보완4: 다계정·병렬규칙)
| 항목 | 값 |
|---|---|
| env 키 | `COUPANG_ACCESS_KEY`, `COUPANG_SECRET_KEY`, `COUPANG_VENDOR_ID` |
| 헤더 형식 | `Authorization: CEA algorithm=HmacSHA256, access-key=…, signed-date=…, signature=…` |
| 서명/토큰 | 요청마다 서명(토큰 없음). message = datetime+METHOD+path+query |
| **다계정 모델** | 계정별 env prefix (`_MAIN` / `_2` …). 같은 셀러 중복계정은 `_client_identity` 로 1회만 |
| **병렬 규칙** | ⚠️ 계정 **순차 조회 필수** — 병렬 시 429로 전체 다운 |

### 표3. 기능 ↔ 엔드포인트 지도 (← 보완1: 성공판정, 보완2: 신뢰도)
| 작업 | METHOD | 경로 | 식별자(구분자) | **성공판정** | **신뢰도** | 비고 |
|---|---|---|---|---|---|---|
| 상품상세 | GET | `/…/seller-products/{sellerProductId}` | sellerProductId | `code==SUCCESS` & items[] 존재 | ②코드 | items[]에서 vendorItemId 수집 |
| 가격수정 | PUT | `/…/vendor-items/{vendorItemId}/prices/{price}` | vendorItemId | HTTP200 **그리고** 본문 code 확인 | ①문서 | 변경비율 -50~+100% 초과 시 400 |
| 송장전송 | (예: 11번가) | … | 배송번호 dlvNo | ⚠️ **-3308/-3309=성공, -3313=실패**(HTTP200이어도 실패) | ③라이브 | 거짓성공 함정 |

> **성공판정 칸이 핵심**: "무엇을 보면 *진짜* 성공인지"를 작업마다 못박는다. HTTP 200 ≠ 성공인 마켓이 다수(11번가·쿠팡).
> **신뢰도 배지**: `①문서`(API문서만·미검증) < `②코드`(우리 코드에 구현됨) < `③라이브`(실계정 왕복검증). 기능 구현 시 ③ 아니면 경고.

### 표3b. 식별자 지도 (← 보완3: 식별자 체인·함정)
| 식별자 | 무엇 | 어디서 얻나 | 잘못 쓰면(함정) |
|---|---|---|---|
| sellerProductId | 쿠팡 상품번호 | 사용자 입력 | — |
| vendorItemId | 쿠팡 옵션ID | 등록 후 상품상세 **2차 GET** | 등록 응답엔 없음 → 안 부르면 옵션 매칭 실패 |
| (스스) A.id | 채널상품번호 | `__PRELOADED_STATE__.simpleProductForDetailPage.A.id` | `productNo`를 쓰면 204 빈응답 → 재고 999 둔갑 |
| (롯데온) dlvNo | 배송번호 | 진행단계 조회 | 송장전송에 `invcNo`를 쓰면 실패 |

### 표4. 구분자 사전 ⭐ (← 보완2: 신뢰도)
| 구분 | 마켓코드 | 마켓라벨 | **평문 뜻** | 우리 통일상태 매핑 | 신뢰도 |
|---|---|---|---|---|---|
| 주문상태 | `INSTRUCT` | 배송지시 | 발송 요청됨, 송장 대기 | 배송준비중 | ②코드 |
| 클레임상태 | `RU` (11번가 등) | 반품요청 | 구매자가 반품 신청함 | 반품요청 | ①문서 |
| 배송사 | `CJGLS` | CJ대한통운 | 택배사 코드 | — | ②코드 |

> **모든 enum 은 여기 한 표에.** 주문상태·클레임상태·배송사·판매상태 등 구분(카테고리)별로 묶어 나열.
> **평문 뜻이 이 문서의 존재 이유** — 미래의 Claude 가 코드만 보고 의미를 복원할 수 있어야 한다.

### 표5. 필드 사전
| 필드명 | 타입 | 필수 | 뜻·출처 | 쓰이는 작업 |
|---|---|---|---|---|
| displayCategoryCode | int | ✅ | 쿠팡 카테고리 코드 | 상품등록 |
| salePrice | int | ✅ | 판매가(10원 단위) | 등록·가격수정 |

### 표6. 응답 · 에러 · 안전장치
| 코드/상황 | 의미 | 처리 |
|---|---|---|
| 400 + "변경비율" | 가격 변동 과다 | manual_review_required = True |
| 429 | rate limit | Retry-After 존중, 순차 재시도 |
| **HTTP200 + 실패코드** | 거짓성공 | 본문 코드까지 확인 후에만 성공 처리 |

### 표7. 코드맵 (문서 ↔ 실제 코드)
| 작업 | 우리 구현 파일:라인 |
|---|---|
| 인증 | `shared/platforms/coupang/auth.py:57-95` |
| 가격수정 | `shared/platforms/coupang/prices.py:33-62` |

### 작업별 상세 블록 ⭐⭐ (F12 를 없애는 핵심 — 필수)
표3의 **모든 작업**은 아래 상세 블록을 반드시 가진다. **이것이 이 문서의 존재 이유** — 여기에 실제 요청/응답이 다 있으면 F12 재방문이 사라진다.

각 작업 블록 구성(필수 4종):
1. **실제 요청** — method·전체 경로·모든 파라미터/바디 (사용자가 F12/문서에서 붙여넣은 **원본 그대로** ```json 블록```).
2. **실제 응답** — F12 에 뜬 **응답 JSON 전체** (일부 잘라내지 않음).
3. **응답 필드 뜻** — 응답 JSON 의 **각 키**가 무슨 값인지 표 (`키 / 뜻 / 예시값`).
4. **성공판정** — 이 응답에서 *진짜 성공*을 어떻게 아는가 (거짓성공 함정 포함).

````
<details><summary>판매자 문의목록 조회 (apiNo=…)</summary>

**실제 요청**
GET https://.../customer/v1/getSellerInquiryList?startDate=…&endDate=…
헤더: Authorization: Bearer {API_KEY}, TR_NO: {TR_NO}

**실제 응답** (F12 원본)
```json
{ "code":"200", "data":{ "inquiries":[ {"inquiryNo":123,"title":"…","content":"…","status":"NEW"} ] } }
```

**응답 필드 뜻**
| 키 | 뜻 | 예시값 |
|---|---|---|
| data.inquiries[].inquiryNo | 문의 고유번호 | 123 |
| data.inquiries[].status | 문의 상태(NEW=미답변) | "NEW" |

**성공판정**: `code=="200"` 그리고 `data.inquiries` 존재. (HTTP200 이어도 code 확인 필수)
</details>
````

> **완성 게이트**: 위 4종(요청·응답·필드뜻·성공판정)이 없으면 그 작업은 표에서 **`①문서` 이하로 취급**하고 "미완"으로 남긴다. 4종이 다 차야 그 API 는 "다시 F12 볼 필요 없음" 상태가 된다.

## 6. 운영 규약 (← 보완6, 이 체계의 사용 방식)

**A. 문서 채우기 (사용자 = 노가다 붙여넣기 / Claude = 구조화)**
1. 사용자가 **원본 그대로 붙여넣음** — 공식 문서 캡처·복붙, F12 콘솔의 실제 요청/응답 JSON. 가공하지 않아도 됨.
2. Claude 가 해당 `{market}.md` 를 채운다:
   - 표3~7 (엔드포인트·구분자·필드·성공판정·신뢰도·코드맵).
   - **작업별 상세 블록**(실제 요청·실제 응답 JSON·필드 뜻·성공판정) — **완성 게이트 4종**을 채워야 그 작업 완료.
   - **모든 코드/구분자·응답 필드에 평문 뜻**.
3. **우리 코드와 대조.** 충돌 시 규칙: **문서=의도 / 코드=현실 / 라이브=진실**. 임의로 하나 고르지 말고 ⚠️ 로 플래그하고 사용자에게 보고.
4. `_index.md` 매트릭스 갱신.

**B. 기능 구현 (사용자 → Claude)**
1. 사용자: "X 기능 추가해줘".
2. Claude: 해당 `{market}.md` 만 읽어 구현. **원본 API 문서 재열람 불필요**.
3. 근거 코드/구분자의 신뢰도가 `③라이브` 가 아니면 → "미검증 근거 위 구현" 경고 후 진행.

- [ ] **완성 게이트**: 채운 작업마다 상세 블록 4종(실제 요청·실제 응답 JSON·필드 뜻·성공판정) 존재 — **F12 다시 볼 것 0**.
- [ ] 모든 enum/구분자·응답 필드에 평문 뜻 존재(빈칸 0).
- [ ] 모든 작업 행에 신뢰도 배지 존재.
- [ ] `_index.md` 매트릭스로 커버리지 한눈에.
- [ ] 구 `_schema.yaml`/`*.yaml` 삭제(진실 원천 1곳).

## 8. 인앱 「데이터 코드 지도」(map.html)와의 관계

- **역할 분리(중복 아님)**: `.md` = **깊은 완성 데이터**(실제 요청/응답까지 — F12 를 없애는 곳). map.html = **얕은 커버리지 화면**(어떤 API 가 씀/안씀인지 한눈에). 담는 *깊이*가 달라 같은 사실을 두 번 적는 게 아니다.
- **연결**: map.html 의 각 API 행 → "자세히" 링크가 해당 `{market}.md` 의 그 API 상세 블록(앵커)으로 점프. 그래서 "지도 봐" 하면 결국 완성 데이터에 닿는다.
- **공유되는 얕은 사실**(엔드포인트명·신뢰도 dot)만 양쪽에 존재 → 갱신 시 함께 손본다. (완전 자동 동기화는 아래 범위 밖.)

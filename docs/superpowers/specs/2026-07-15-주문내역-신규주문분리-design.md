# 주문내역 재정의 #1 — 「주문일 = 신규 주문」 분리 (design)

> **계층**: 프로젝트 스펙 / **날짜**: 2026-07-15
> **상위 발화**: 주문내역 3분리 요청 (①주문일=신규주문 ②상태변경 별도탭 ③마켓별 CS탭)
> **본 스펙 범위**: **①번만**. ②·③은 별도 스펙(순서 B — 1→2→3).
> **관련 메모리**: [[project_marketplace_order_status_unification]], [[project_multi_account_orders_20260710]], [[project_delivery_inspection_tab_20260712]]

## 1. 목표 (한 줄)

주문내역의 **주문일 목록**을 「그 기간에 실제로 들어온 주문(주문 발생일 기준)」만으로 정리한다. 취소/교환/반품 같은 **상태변경 이벤트 행**은 이 목록에서 빼서, 기능 #2(상태변경 별도 탭)가 소비할 수 있도록 데이터 원천에서 갈라 놓는다.

## 2. 확정된 정의 (사용자 결정)

- **신규 주문 = 그날 주문이 들어온 건. 주문상태는 무관.**
  - 주문일 = **주문 발생 시각**(주문 생성/접수일). 마지막 상태변경 시각이 아님.
  - 나중에 취소/반품/교환돼도 그 주문은 **원래 주문일 목록에 그대로 남는다**(상태 배지만 바뀜). 상태로 걸러내지 않는다.
- **세는 단위 = 옵션 줄**(현재 방식 유지). 같은 주문의 상품·옵션마다 한 줄. KPI 「신규주문 N건」도 옵션 줄 기준.
- **상태변경(취소/교환/반품) 활동**은 별도 개념 → 기능 #2 탭이 **변경일 기준**으로 관리. 기능 #1에서는 **주문일 목록에서 제거만** 하고, UI로는 보여주지 않는다(사용자 결정: #2까지 완전 미루기).

## 3. 현재 구조 (as-is)

- `lemouton/markets/order_export.py`
  - 마켓별 빌더(`smartstore_order_rows` / `lotteon_order_rows` / `coupang_order_rows` / 11번가·ESM 등)가 **주문 행**과 **클레임 행**(`_claim_row` 등, 주문상태=취소/교환/반품 요청·완료)을 **한 리스트에 섞어** 만든다.
  - `combined_order_rows(markets, …)` → `_fetch_combined(…)`(마켓 합침) → `_filter_by_order_date(rows, since, until)`(주문일 트리밍).
- 이 `combined_order_rows` 한 함수를 **네 곳이 공유**:
  1. `webapp/routes/orders.py :: /orders/preview.json` — 화면 주문 목록(list 탭).
  2. `/orders/export.xlsx` — 엑셀 내보내기.
  3. `lemouton/delivery/market_enrich.py` — 배송검사 enrich.
  4. `lemouton/margin/sell_source.py` — 마진 판매·소싱.
- 문제: 클레임 이벤트가 주문 목록에 섞여 「신규 주문 유입」 뷰가 오염된다. #2·#3을 얹으려면 원천에서 갈라야 한다.

## 4. 설계 (to-be)

### 4.1 데이터 계층 — 성격 태그 (seam)

각 마켓 빌더가 만드는 모든 행에 태그를 부여한다.

| 필드 | 값 | 의미 |
|------|-----|------|
| `_kind` | `'order'` | 주문 유입 행(결제완료·배송준비중·배송중·배송완료·구매확정). **이 주문이 나중에 취소돼도 `'order'` 유지**(140 진행단계 덮어써 상태가 취소완료여도 종류는 order). |
| `_kind` | `'change'` | **클레임 API에서 온** 취소/교환/반품 **이벤트** 행. |
| `_change_date` | `str`(YYYYMMDDHHMMSS 등) | `_kind='change'` 행에만. **변경일 = 클레임 접수일**(스스 `claimRequestDate`류 / 롯데온 `clmReqDttm` / 11번가·쿠팡 대응 필드). #2가 이 값으로 변경일 트리밍·정렬. |

- 판정 규칙: **클레임 API 경로에서 생성된 행만 `'change'`**. 주문/배송 API에서 온 행은 상태가 취소완료·반품완료여도 `'order'`.
- 태그는 빌더 내부에서 부여(마켓마다 클레임 생성 지점이 명확: `_claim_row`, 쿠팡 `receiptType`/`exchangeStatus` 경로, 스스 claim 경로, 11번가 cancel/return 엔드포인트 경로).

### 4.2 신설 함수 — `new_order_rows`

```
new_order_rows(markets, *, days/since/until/use_cache/… ) -> list
    = combined_order_rows(같은 인자) 결과에서 _kind != 'change' 만 남긴 것
```

- **얇은 필터**로 구현한다(재fetch 없음). `combined_order_rows`의 TTL 캐시·경고 전파를 그대로 재사용 → 화면↔엑셀 캐시 공유·조용한 실패 방지 로직을 건드리지 않는다.
- 주문일 트리밍은 이미 `combined_order_rows` 안에서 `_filter_by_order_date`로 끝나므로 추가 트리밍 불필요.

### 4.3 화면 배선

- `/orders/preview.json`가 `combined_order_rows` → **`new_order_rows`** 호출로 교체(오직 이 엔드포인트만).
- **바뀌지 않는 것**(회귀 방지): `/orders/export.xlsx`, `market_enrich`, `margin/sell_source`는 **`combined_order_rows` 그대로** 사용(전체 집합 필요).
- 결과(사용자 체감):
  - 주문 목록이 「그 기간 실제 유입 주문」만(옵션 줄)으로 깔끔해짐. 취소/교환/반품 **churn 이벤트 행 사라짐**.
  - 취소된 주문 **자체**는 주문일에 남고 상태 배지만 취소완료.
  - KPI 「신규주문 N건」이 유입 건수(옵션 줄)로 정확해짐.

### 4.4 `status_change_rows` 는 #2 소유 (본 스펙에서 미구현)

- `_kind='change'`·`_change_date` **태그는 #1에서 심는다**(클레임 빌더를 이미 건드리므로 저렴). 하지만 **`change` 행을 변경일 기준으로 모아 주는 함수/탭은 기능 #2** 소관이다.
- 이유: `combined_order_rows`는 **주문일**로 트리밍하므로, 「주문일은 창 밖 + 변경일은 창 안」인 클레임(옛 주문의 오늘 취소)은 여기서 이미 탈락한다. 변경일 기준 수집은 별도 fetch 설계가 필요 → #2에서 정의.

## 5. 엣지 케이스

| 상황 | 처리 |
|------|------|
| 창 안 주문이 나중에 취소(140이 배송행 상태를 취소완료로 덮음) | `_kind='order'` 유지 → 주문일 탭에 **남음**(배지 취소완료). 별도 클레임 이벤트는 #2. |
| 옛 주문(주문일 창 밖)이 창 안에서 취소 → 클레임 API로만 등장 | `_kind='change'`. `combined`의 주문일 트리밍에서 탈락 → 주문일 탭에 **안 나옴**(정상, 이 기간 신규 아님). #2가 변경일 기준으로 잡음. |
| 같은 주문·같은 옵션 중복 | 기존 dedupe(주문번호+옵션/vendorItemId 1회) 그대로. |
| 클레임 조회 실패 | 기존 `try/except`로 활성 주문 유지(현행 유지). 태그만 추가되므로 영향 없음. |

## 6. 테스트 (TDD, `tests/…`)

1. **태그 정확성**(마켓별 fixture): 주문/배송 API 행 → `_kind='order'`(상태가 취소완료여도); 클레임 API 행 → `_kind='change'` + `_change_date` 채워짐.
2. **`new_order_rows`**: `change` 행 제외, `order` 행(취소된 배송행 포함) 유지. `combined_order_rows`와 동일 인자·캐시 경로.
3. **`/orders/preview.json`**: `new_order_rows` 사용 → 응답에 `_kind='change'` 행 없음. KPI 신규주문 카운트 = order 옵션 줄 수.
4. **회귀**: `combined_order_rows` 출력 불변 → 기존 `test_order_export`·`test_market_enrich`·엑셀·마진 테스트 전부 그린.

## 7. 비목표 (Non-goals — 이번 스펙 아님)

- 상태변경(취소/교환/반품) **별도 탭 UI**, 3단계 워크플로(신규요청→대응필요[수기체크+메모]→대응완료) → **기능 #2**.
- `status_change_rows` **변경일 기준 수집 함수** → 기능 #2.
- 마켓별 **CS(문의) 탭·발송 API** → 기능 #3.
- 주문일 목록의 시각/레이아웃 재디자인(색·정렬 UI 손질) — 데이터만 교체, UI 구조 유지.

## 8. 구현 메모

- 구현은 **`main` 기준 새 워크트리**에서 분기(현재 `feature/crawl-worker-queue`는 stale — 메모리 [[project_crawl_worker_queue_branch_stale]]). 이 스펙 문서 커밋은 현재 트리에 남겨도 무방.
- 완료 기준(프로젝트 규율): 배포 + `mou-m.com` 라이브에서 주문일 목록에 클레임 churn 행이 사라지고 취소된 주문 자체는 남는지 육안 검증.

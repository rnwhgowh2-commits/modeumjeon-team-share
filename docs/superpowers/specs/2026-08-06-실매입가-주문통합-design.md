# 실매입가 주문 통합 — 설계서

> **작성**: 2026-08-06 (사장님 브레인스토밍 확정)
> **범위**: 실매입가를 주문 라인에 저장 → 주문내역·상품관리가 공유 · 마진 판정을 주문내역 가로탭으로
> **상태**: 설계 확정, 구현 전

## 1. 왜 (문제)

지금 실매입가(진짜 사온 값)는 **마진 계산기 회차 안에만** 산다. 그래서:

| 문제 | 실측 근거 |
|---|---|
| 🔴 **최근 20회차만 남고 옛것은 자동 삭제** | `lemouton/margin/store.py:21` `KEEP_RECENT = 20` + `_prune()` (:107). 사장님 요구 「항시 저장」과 정면 충돌 |
| 🔴 **주문내역·상품관리가 매입가를 못 본다** | 매입가는 `margin_analyses.result_blob`(gzip JSON) 안. 주문 라인(`MarketOrderLine`)에 붙은 값이 아님 |
| 🔴 **상품 단위 실현마진 불가** | `lemouton/margin/*` 에 `model_code`·`canonical_sku` 개념 없음. 상품 축 = 상품명에서 뽑은 5자리 숫자(`matcher.extract_product_code:61-69`) |

🟢 **이미 돼 있는 것** — 매출 쪽은 이미 통합돼 있다. 마진 계산기는 마켓 API를 따로 부르지 않고
**주문 적재분(`MarketOrderLine`)을 읽는다** (`margin/sell_source.py:407-420` → `order_source.fetch_rows` → `order_store.load`,
`MARGIN_LIVE_TAIL_DAYS = 0` :404). 즉 매입가만 따로 놀고 있다.

## 2. 사장님 확정 규칙 (원문 기준)

1. 마진계산기 기능 **그대로** 한다
2. 매입가 입력 = **수기** or **더망고 엑셀 업로드**
3. 데이터는 **항시 저장**된다
4. 매입가 입력 전에는 **소싱처 URL 최종매입가**로 한다
5. 사입인 경우 **사입매입가**로 한다
6. **오픈마켓주문번호 + 상품(옵션)별**로 실매입가가 입력되면, 실마진이 필요한 곳에 **데이터 공유**한다

추가 확정:
- 저장 = **전용 저장소**(A안). 화면 = **주문 표에 매입가 열 + 네모 입력칸(바로 수정)**
- 마진 계산기 탭은 **당분간 유지**(새 방식 검증 후 정리)

## 3. 데이터 설계

### 3.1 신규 테이블 `order_line_purchases`

주문 라인 1줄 = 1행. **주문번호 단독 키 금지**(다품목 주문 라인이 서로를 덮어씀 —
`models_orders.py:27-28` 경고) → 열쇠는 `line_uid`.

| 컬럼 | 타입 | 뜻 |
|---|---|---|
| `line_uid` | String(200) PK | 주문 라인 열쇠 (`MarketOrderLine.line_uid`) |
| `purchase_price` | Integer | 실매입가 (원). NULL 금지 — 값 없으면 행 자체를 안 만든다 |
| `source` | String(16) | `manual`(수기) / `mango`(더망고 엑셀) |
| `mango_ref` | String(255) | 엑셀 출처 추적 (파일명 + 행번호). 수기면 NULL |
| `memo` | String(255) | 사장님 메모 |
| `input_by` | String(120) | 입력자 |
| `created_at` / `updated_at` | DateTime | |

- 인덱스: `line_uid`(PK) + `source`
- **주문 재수집에 안 지워진다** — `order_store.save`는 `market_order_lines`만 건드리고 이 표는 안 본다
- 이력이 필요하면 2단계에서 `order_line_purchase_history` 추가 (이번 범위 밖)

### 3.2 왜 별도 표인가 (B·C안 기각 사유)

- **B안(주문 줄 JSON 안에 끼워넣기) 기각**: 주문은 주기적으로 재수집되고 그때 `row` JSON이
  통째 교체된다 → **사장님이 입력한 값이 조용히 증발**. 「조용한 실패」 부류(메모리: `project_silent_failure_bug_class`)
- **C안(`market_order_lines`에 컬럼 추가) 기각**: 출처·입력시각·메모를 못 남기고,
  같은 정보가 적재 테이블에 섞여 재수집 로직과 얽힌다
- **A안 채택**: 적재(기계가 쓰는 것)와 입력(사람이 쓰는 것)을 물리적으로 분리 → 서로 못 덮어씀

## 4. 매입가 우선순위 (규칙 4·5) — **2026-08-06 사장님 재확정: 「싼 쪽」**

한 주문 라인의 매입가를 물으면 이 순서로 답한다. **어느 값인지 화면이 항상 밝힌다.**

| 순위 | 값 | 원천 | 화면 표기 |
|---|---|---|---|
| 1 | 실매입가 | `order_line_purchases.purchase_price` (사람이 적은 값) | **실매입가** (검정·확정) |
| 2 | **사입가·소싱가 중 싼 쪽** | 판정 = `pricing.cost_basis.resolve_cost_basis` 호출 | 뽑힌 쪽을 그대로 — 사입이면 **사입가**(회색), 소싱이면 **최종매입가(예상)**(연한 색 + 「예상」 표) |
| — | 없음 | 둘 다 못 구함 | 「확인 불가」 (0으로 채우지 않는다) |

🔴 **왜 바뀌었나 (옛 규칙: 「사입이 있으면 무조건 사입가」)**
그 규칙은 이 문서(1차 설계) 안에만 있었고, 프로그램의 원가 규칙 단일 원천인
`lemouton/pricing/cost_basis.py`(2026-07-20 사장님 확정)는 처음부터 **「둘 다 있으면 싼 쪽」**이었다.
그대로 두면 판매가·마진 화면(`api_pricing`·`uploader.preview`·`uploader.reconcile`)과
주문내역 매입가 칸이 **같은 상품에 다른 원가**를 보여 준다. 사장님 재확정으로 **「싼 쪽」에 통일**하고,
`markets/purchase_price.py` 는 판정을 다시 구현하지 않고 `resolve_cost_basis` 를 **호출만** 한다.

🔴 **이건 「폴백 금지」 원칙 위반이 아니다.** 금지되는 폴백은 *크롤 실패 시 대표가(평균·최저)로 메우는 것*이고,
여기는 **성격이 다른 값들에 규칙을 준 뒤 출처를 밝히는 것**이다. 다만:
- 소싱 예상가로 계산한 마진은 **「예상 마진」으로만** 표기하고 실적 숫자에 섞지 않는다
- 합계·집계에서 예상가 기반 건수는 **따로 센다**(「예상 N건 포함」)

## 5. 입력 두 경로

### 5.1 수기 입력 (주문 내역 표)

- 주문 표에 **「매입가」 열** 추가 → 셀이 네모 입력칸(마진 계산기와 같은 방식)
- 저장: `POST /orders/api/purchase-price` `{line_uid, price, memo?}` → upsert, `source='manual'`
- 🔴 **주문 라인 인라인 편집·저장 엔드포인트는 현재 0개**(조사 확인) — 새로 만든다
- 빈 값으로 저장하면 행 삭제(= 실매입가 없음으로 되돌림)

### 5.2 더망고 엑셀 업로드

- 파서는 **기존 것 재사용** — `lemouton/margin/buy_parser.py::parse_buy`
  (필수 열 7개: 마켓주문일자·마켓명·마켓주문번호·수령인명·마켓상품명·옵션1·**구매가격**)
- 🟢 **엑셀에 「실매입가」 열을 새로 추가할 필요 없다** — 더망고 엑셀의 `구매가격`이 곧 실매입가다
  (사장님 표현 「실매입가 머리글 열 추가」 = 화면 표의 열. 엑셀 포맷은 그대로)
- 매칭도 **기존 규칙 재사용** — `matcher.match_data` 3단계
  ① 주문번호 + 상품코드 + 옵션 ② 주문번호 + 상품코드 ③ 주문번호
  (스마트스토어 `A(B)` 주문번호는 A·B 둘 다 후보 — `order_match_keys:37-47`)
- 매칭 결과 → 그 매출 행의 `line_uid` 확정 → `order_line_purchases` upsert, `source='mango'`
- 🔴 **못 붙은 매입 행은 버리지 않는다** — 「못 찾음」 목록으로 보여주고 손으로 주문 줄 지정 가능
- 🔴 **센티널 `999999999.99` → 0 규칙 유지**(`buy_parser.py:29-40`) — 0은 「입력 안 함」으로 취급, 행 안 만듦

## 6. 화면

### 6.1 주문 내역 가로 탭 4개

`/orders?tab=list` 안에서 가로 탭으로 가른다 (마진 계산기 판정 규칙 그대로 재사용):

| 탭 | 내용 |
|---|---|
| 전체 | 지금 주문 목록 + 매입가 열 |
| 이상마진 | 마진율이 정상 범위를 벗어난 건 |
| 블랙스팟 | 매출·정산 0인데 매입만 있는 건 (돈 못 받음) |
| 매입가 미입력 | 실매입가가 없는 건 — **채워야 할 것 모아보기** |

- 판정 로직은 `margin_embed.html`·`margin_rules.js`의 것을 **읽어서 서버로 옮긴다**(재구현 아님 — 같은 임계값)
- 마진 계산기 탭은 **그대로 둔다**(사장님 확정 a) — 새 방식이 라이브에서 검증되면 그때 정리

### 6.2 상품관리 판매 이력 (공유)

- 「실현 마진」 열을 채운다: `정산 예정 − 실매입가` (그 상품 주문 라인들의 합)
- 매입가 없는 건은 **0으로 채우지 않고** 「매입가 미입력 N건」으로 표기 + 주문내역 「매입가 미입력」 탭 링크
- 상품 축 = 주문 라인 → `canonical_sku` → `model_code` (`price_diff.resolve_targets_verbose` 재사용)

### 6.3 용어 — 최종매입가 ≠ 순마진 예상가 (2026-08-06 사장님 확정)

> **최종매입가** = 소싱처 표면노출가 − 혜택 → **매입 원가**
> **순마진 예상가** = 정산예정금액(배송비 포함) − 최종매입가 → **마진**
>
> 둘은 **다른 값**이다. 매입 원가 자리에는 언제나 **「최종매입가」**를 쓴다.

🔴 이 문서의 1차 초안은 「소싱처 크롤 최종매입가 표기 → **순마진 예상가**」라고 적었는데
**그 항목 자체가 틀렸다**(원가 자리에 마진 이름을 붙였다). 그대로 구현한 PR#857 이
화면 용어를 바꿨다가 **PR#894 에서 되돌렸다**. 원가 자리의 이름은 「최종매입가」다.
「실매입가」(사람이 적은 실제 매입가)와 구분해야 할 때는 **「최종매입가(예상)」**로 적는다.

## 7. 3단계 구현 (단계마다 배포·검증)

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **1** | 저장소 + 수기 입력 + 더망고 업로드 매칭 | 주문 표 매입가 칸에 입력·저장되고, 엑셀 올리면 자동 매칭돼 저장. 재수집해도 안 지워짐 |

## 8. 지키는 원칙

- **값 지어내기 금지** — 매입가 없으면 「확인 불가」·「미입력」. 0 채움 금지
- **재계산 금지** — 정산예정금(`정산예정금(배송비포함)`)·마진율 임계값은 기존 값을 읽기만
- **중복 저장 금지** — 매입가의 단일 원천은 `order_line_purchases` 하나
- **원가 규칙 단일 원천** — 사입 vs 소싱 판정은 `pricing/cost_basis.resolve_cost_basis` 하나.
  같은 규칙을 두 번 구현하지 않는다(§4 재확정 사유)
- **같은 정보 두 화면 = 같은 값** — 상품관리·주문내역·마진 계산기가 같은 저장소를 본다
- DB 변경은 `shared/db.py:init_db()` create_all + `_apply_lightweight_migrations` 규약(Alembic 없음)

### 9.1 🔴 마진 계산기 탭을 왜 안 없앴나 (2026-08-12 판단)

이 문서 1차안은 「새 방식 검증 후 마진 계산기 탭 정리」라고만 적었는데, 실제로 열어 보니
그 화면에는 **주문 내역으로 옮겨진 적이 없는 기능이 11개**나 있었다 —
요약 · 전체내역 · 일별 · 월별 · 브랜드별 · 금액대별 · 상품별 · 마켓별 · 소싱처별 · 블랙스팟 · 설정.
탭을 안내문으로 바꿨으면 **그 기간 집계가 통째로 사라졌을 것**이다.

그래서 「정리」를 이렇게 했다:

1. **역할을 갈라 밝힌다** — 탭 위 배너 + 탭 설명: 실매입가 입력·이상마진·블랙스팟은
   주문 내역, 기간 집계·분석은 마진 계산기.
2. 🔴 **저장소를 합친다**(더 중요) — 마진 계산기에 올린 매입 엑셀도
   `order_line_purchases` 에 같이 저장한다(`api_margin._share_to_purchase_store` →
   `purchase_mango.apply`, 같은 코드). 안 그러면 같은 엑셀을 올려도 **마진 계산기만 알고
   주문 내역·상품관리는 모르는** 상태가 되어 §8 「같은 정보 두 화면 = 같은 값」이 깨진다.
3. 완전 제거는 **집계까지 옮긴 뒤** 한다.

> **사장님 확정 (2026-08-12)** — 「마진 계산기 탭 **나중에 삭제**」.
> 즉 ①지금은 그대로 둔다 ②집계 11개를 주문 내역으로 옮긴다 ③그 뒤에 탭을 없앤다.
> 🔴 ②를 건너뛰고 ③을 하면 안 된다 — 그 순간 기간 집계가 사라진다.

### 9.2 곁다리로 잡은 것 — 롯데온 카테고리는 「못 받는 값」이 아니었다

상품관리 「마켓 등록·정책」 탭은 롯데온에 대해 「마켓이 카테고리를 안 알려줘요」라고
말하고 있었다. 목록 API(`lotteon.product.list`)에 필드가 없는 건 맞지만,
**상세(`lotteon.product.get_detail`)에는 `scatNo`·`dcatLst` 가 온다** — 상품 등록이 본보기
상세의 그 두 필드를 그대로 복사해 라이브에서 성공했다(2026-07-21 LO2729045338).
즉 **오는 값을 우리가 안 받고 있었을 뿐**이다.

이제 판매가를 채우는 그 상세 호출에서 카테고리도 같이 거둔다

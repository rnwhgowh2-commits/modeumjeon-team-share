## 1. 배경 / 문제

크롤링 가이드의 **데이터 지도(재고·가격 탭)** 가 "**무엇을** 어디서 긁는지"는 적혀 있으나,
"**왜** 소싱처마다 이 방식(API/HTML/DOM)인지", 그리고 **로그인·수집위치가 데이터 종류별로 갈린다는 점**이
빠져 있고, 일부는 **실제 코드와 어긋나** 있다.

코드(`origin/main`) 실측으로 확인한 핵심:
- **로그인·수집위치는 소싱처 단위가 아니라 "재고·표면가 vs 혜택" 데이터 종류 단위로 갈린다.**
  (재고·표면가 = 대부분 무로그인·서버 / 혜택 = 로그인·확장)
- 가이드 보기가 **SSG·SSF를 "로그인 필요·크롬확장"으로 오기** (실제는 무로그인·서버 curl_cffi).
- 롯데온·스마트스토어는 main에서 **한정수량을 못 잡아 999 둔갑** (롯데온 999는 대체상품 가드로 ⚠️확인필요 처리).
- **현대H몰·롯데아이몰**(신규)이 §1 재고표에 없음.

## 2. 확정된 결정 (사용자)

| 결정 | 내용 |
|---|---|
| 재정의 기준 | **현재 main 라이브 현실 + "개선예정" 병기** (목표상태로 안 적음 — 가이드가 거짓되면 안 됨) |
| 작업 범위 | **가이드 재정의 + 40 URL 라이브 검증까지 한 사이클**. 코드 수정은 검증 결과 보고 별도 결정 |

## 5. Phase 1 — 40 URL 라이브 검증 (읽기 전용)

**목표**: 코드-실체가 **사이트-실체와 맞는지** 확인 → 정답표 + 코드 수정 후보 확정.

**절차**
1. 로그인된 `mou-m.com` 브라우저(사용자 선택)에서
   `GET /api/bundles/르무통_메이트/option-matrix` 전수 읽기 (40 URL: 르무통1·스스1·무신사10·SSF9·롯데온9·SSG10).
   각 `options[].sources[]`의 `crawled_stock/price/stock_state/last_status` 수집.
2. **의심 항목 자동 추림**:
   - 롯데온: ⚠️확인필요(999 둔갑) 비율
   - 스마트스토어: 전부 999 여부
   - SSG: SSG MONEY 등 혜택 0/미갱신
   - 전 소싱처: 크롤실패·옵션없음·한정수량 누락·999 둔갑 의심
3. **의심분만 실페이지 대조**: 실제 소싱처 상세 페이지(로그인 브라우저)와 비교.
   - 환경 제약: claude-in-chrome은 ssg.com·brand.naver.com 차단 → 해당 소싱처는
     사용자 육안 또는 라이브앱 값으로 한정. Playwright는 무신사·롯데온 WAF 타임아웃.
4. 산출물: **정답표**(소싱처×데이터종류: 일치/불일치/근거) + **코드 수정 후보 목록**(우선순위).

**무결성 기준(검증 통과 정의)**: 라이브앱 값과 실페이지가 100% 일치하면 PASS.
불일치 시 셀·센티넬·파싱 어느 층의 문제인지 분류(저장 vs 크롤 vs 표시).

> 본 Phase는 코드/문서 수정 없음. 검증만.

## 6. Phase 2 — 가이드 재정의 (보기 + 원문 동시)

현재 카드 구조·디자인 톤 유지. 기존 CSS 클래스 재사용(`.scard`/`.axes`/`.why`/`.meta`/`.pill`).

### 6-1. 보기 `map.html` — 2 재고 / 3 가격 탭
1. **로그인·위치 배지를 "데이터 종류별"로 재정의**: 카드 상단 단일 "로그인 필요" 배지 →
   **`재고·표면가`(무로그인·서버 등) / `혜택`(로그인·확장 등)** 2축으로 분리.
   - SSG·SSF: "무로그인·서버 curl_cffi"로 정정.
   - 무신사: 재고·표면가 무로그인 / 혜택 로그인.
2. **"왜 이 방식?" 한 줄** 각 소싱처에 추가(기존 `.why` 박스 톤). 예:
   - SSG="재고·가격이 SSR HTML JS블록(`uitemObj.usablInvQty/bestAmt`)에 다 박혀 옴 → 서버 무로그인 정규식이 가장 견고"
   - 롯데온="옵션 API가 `disabled`(품절여부)만 주고 수량은 비공개 → 한정수량 못 잡음"
3. **`개선예정` 배지**: 롯데온·스마트스토어("한정수량 못 잡음·999 둔갑"), 현대H몰("feature 미머지").
4. **현대H몰·롯데아이몰 카드 신설**(롯데아이몰=main, 현대H몰=개선예정).

### 6-2. 보기 — 2 재고 탭 상단 "왜 소싱처마다 다른가" 안내(작게)
4가지 기준 한 줄씩: ①전용 API 공개? ②내장 구조데이터 있나? ③WAF/봇차단? ④로그인=혜택만.

### 6-3. 보기 — 7 신규추가 탭: **수집 방식 판정 래더(성능 우선순위)** 신설
URL을 받으면 **위 순위부터 적용 가능 여부를 따져 가능한 가장 높은 순위 채택**:

| 순위 | 방식 | 적용 가능 판단 | 차단 게이트 | 레퍼런스(어느 형) |
|---|---|---|---|---|
| **1** | 전용 API 직접 호출 | 상세에서 호출되는 내부 JSON 엔드포인트 존재 + 직접 호출 가능 | 방화벽·게이트웨이(현대H몰 api 404)·CORS | 무신사·롯데온형 |
| **2** | 내장 구조 JSON 파싱 | 페이지에 `__NEXT_DATA__`·`option_stock_data`·`uitemObj`·`dataBenefit`·`itemInvQtyInfo` 통째로 존재(서버가 자기 API 부른 결과=정확도 동일) | — | 현대H몰·르무통·SSG·롯데아이몰형 |
| **3** | SSR HTML 정규식/셀렉터 | 구조 JSON은 없지만 raw HTML/JS문자열에 값 존재 | lazy 렌더(렌더본 비어있음) | SSF형 |
| **4** | 렌더 DOM(확장 navGrab) | 위 셋 불가·JS 렌더 후에만 생김 | (최후 수단) | 롯데온 혜택가형 |

**가로지르는 게이트(어느 순위든 적용)**
- **로그인 = 혜택만** → 혜택만 로그인 확장으로 한 단계 내림(재고·표면가는 무로그인 유지).
- **WAF/봇차단** → 서버 fetch 불가 → curl_cffi impersonate 또는 확장 navGrab 강제(롯데아이몰).
- **정량 비공개**(무신사 정상재고·SSF 일반재고) → **999가 정답**, 가짜 숫자 금지.

기존 7탭의 순서도(샘플 URL→4분면→항목추출→혜택종합→매입가→검증)는 유지하고,
2번 단계("수집 방식 분류")를 이 래더로 교체·강화.

### 6-4. 원문 `docs/크롤링-가이드.md`

- **현대H몰·롯데아이몰 행 추가**(§1 재고표·§2 가격표).
- 새 절 **"§6 신규 소싱처 수집 방식 판정 래더"** 추가(6-3과 동일 내용).

## 7. 작업 위치 / 배포

- 가이드(map.html·크롤링-가이드.md)는 **`origin/main`에만** 존재 → 현재 stale feature 브랜치 아님.
- **origin/main 기준 워크트리**에서 작업 → push origin/main (메모리 `[[project_deploy_isolated_change_via_worktree]]`).
- 정본 위치 주의: `프로그램/_시스템/docs/크롤링-가이드.md` (배포 tar에 포함되려면 `_시스템` 안).
- 라이브 검증: 푸시 후 `mou-m.com /sourcing-guide/map` 육안 + 매트릭스 값 대조.

## 8. 무결성 원칙 (준수)
1. 가이드는 **현재 라이브 현실**을 적는다(목표 상태로 거짓 표기 금지). 개선분은 `개선예정`으로 명시.
2. 폴백가 금지·크롤실패 표기·단일 진실 원천·누락 경고(기존 4원칙) 그대로.
3. 정량 비공개 소싱처는 999가 정답 — 가짜 숫자 금지.
4. 코드 수정은 **40 URL 라이브 검증 결과**에 근거해서만(추정 수정 금지).

## 10. 비범위 (이번 사이클 제외)
- 실제 코드(크롤러) 수정은 검증 결과 보고 **별도 결정**(롯데온 stkQty 머지·스스 per-SKU·현대H몰 머지 등).
- SSG/SSF 혜택 저장 배선 수정(기지 결함 F)은 검증으로 재확인만, 수정은 별도.

## 1. 목적 (Why) — 본질 재정립

배송검사의 **본질은 마켓 API 연동**이다. v1은 더망고 엑셀 값(K 송장·M 마켓상태)만으로 검사했으나, 이는 더망고의 과거 스냅샷이라 "지금 마켓에서 실제로 배송흐름이 멈췄는지"를 알 수 없다. v2는 엑셀의 「오픈마켓주문번호」로 **마켓 실주문을 조회**해 실데이터로 검사한다.

사용자 원문 핵심:
> 더망고 엑셀 업로드 → 프로그램에서 「오픈마켓주문번호」 취출 → API 연동해 주문 불러오기 → 해당 주문건에 대해 배송검사.
> 첫 문장: "주문상태 흐름 변경 없는 주문건을 확인하고 싶다."

### 잡아야 할 2가지
1. **이중 송장 방지** — 담당자가 더망고에서 송장 출력 후 「해외현지배송중 → 현지배송완료」로 안 바꾸면, 다음 회차에 같은 건을 또 출력해 **이중 발송**할 수 있다. 송장을 넣으면 마켓 API에 등록되므로, 재출력 대상인데 **마켓엔 이미 송장이 있으면** 중복 경고.
2. **배송흐름 정체** — 2~3일 전 주문건 송장을 미리 입력했는데, 마켓에서 **「배송준비 → 배송중」으로 안 넘어가는** 건(소싱처 품절·지연) 감지.

## 2. 범위 (Scope)

**포함**
- **별도 「배송검사」 탭 → 주문 내역 탭으로 통합·흡수** (탭·사이드바 메뉴 제거). 애초 의도 = 별도 화면이 아니라 주문 내역 안에서 검사→송장 전송 한 흐름.
- 더망고 엑셀 「마켓주문번호」(=오픈마켓주문번호) 취출 → 마켓 API 실주문 조회 → 매칭
- 매칭 결과(마켓 통일상태·마켓 등록송장·조회시각·실패사유)를 MangoOrder에 저장(캐시)
- 검사 2종을 **마켓 실데이터 기준**으로: ①이중송장 ②배송흐름 정체
- 조회 실패 계정 "확인 불가" 정직 표시 + 실패 배너
- 대상 마켓 4개: 스마트스토어·쿠팡·롯데온·11번가

**제외 (YAGNI)**
- 택배사 송장추적 API(스윗트래커) 직접 연동 — 마켓 통일상태로 판단
- 주문상태 통일표 신규 작성 — **이미 존재**(`order_export._STATUS_KO`) 재활용
- 배송방식(까대기/직배) 로직 변경 — v1 그대로

## 5. 매칭 (핵심)

- **키**: 더망고 `market_order_no`(C, 마켓주문번호) = order_export 「오픈마켓주문번호」.
- **마켓 판별**: 더망고 `market_name`(B) → 마켓 슬러그(쿠팡→coupang, 롯데ON→lotteon, 스마트스토어→smartstore, 11번가→eleven11). 매핑표 `_MANGO_MARKET_SLUG`.
- **조회 범위**: 업로드된 엑셀에 등장한 마켓 집합 + 주문일(A) min~max 기간으로 `combined_order_rows` 호출(중복조회 방지).
- **매칭 결과**: 오픈마켓주문번호 → {통일주문상태, 등록송장, 발송처리일시(있으면)}. 미매칭 주문은 `market_check_error="마켓에서 못 찾음"`.

## 6. 저장 모델 (MangoOrder 필드 추가)

기존 `mango_orders` 테이블에 컬럼 추가(SQLite → `shared/db.py:_apply_lightweight_migrations` 에 ALTER 등록):

| 필드 | 설명 |
|---|---|
| `market_api_status` | 마켓 통일 주문상태(예: 배송준비중/배송중/배송완료). 조회 성공 시 |
| `market_api_invoice` | 마켓에 등록된 송장번호(없으면 NULL) |
| `market_shipped_at` | 마켓 발송처리일시(제공 마켓만; 정체 24h 기준시각 우선값) |
| `market_checked_at` | 마지막 조회 시각 |
| `market_check_error` | 조회 실패·미매칭 사유(있으면 "확인 불가") |

## 7. 조회 파이프라인 (업로드 직후)

```
def enrich_from_market_api(session, uploaded_uids) -> dict:
    1. 대상 주문 로드(방금 업로드분) → 마켓별·오픈마켓주문번호 수집
    2. 마켓 슬러그 판별, SUPPORTED 아닌 마켓은 스킵(사유 저장)
    3. 주문일 범위 계산 → combined_order_rows(markets, since, until, warnings=[])
    4. 결과를 {오픈마켓주문번호: row} 인덱싱
    5. 각 MangoOrder 갱신:
       · 매칭됨 → market_api_status/invoice/shipped_at/checked_at, error=None
       · 미매칭 → market_check_error="마켓에서 못 찾음"
    6. warnings(IP미등록·키오류 계정) → 반환(배너 표시용)
```
- **성능**: 계정 순차 조회(병렬 금지 — 429 방지, [[project_multi_account_orders_20260710]]). `use_cache=True`로 대시보드 조회분 재사용.
- **실패 격리**: 한 계정 실패가 전체를 막지 않음. 실패분은 warnings + 그 주문 "확인 불가".

## 8. 검사 로직 (마켓 실데이터 기준)

### ① 이중송장 방지 (find_double_invoice_risk)
- 조건: 더망고 `mango_status == "해외현지배송중"`(재출력 대상 풀) **AND** 마켓 실데이터에서 `market_api_invoice` 존재 **또는** `market_api_status ∈ _SHIPPED_STATES`.
- 의미: 아직 더망고에선 안 바꿔서 재출력될 수 있는데, 마켓엔 이미 송장/배송중 → **이미 발송된 건, 재출력 위험**.
- v1의 uid-송장이력 기반 중복도 유지(엑셀만으로도 잡히는 보강).

### ② 배송흐름 정체 (find_flow_stalled)
- 조건 3개 AND:
  1. 송장 있음(`market_api_invoice` 또는 더망고 K)
  2. `market_api_status ∉ _SHIPPED_STATES`(=배송중 미만, 발송처리/배송준비중에 멈춤)
  3. **기준시각 + 24h < now** — 기준시각 = `market_shipped_at`(있으면) 우선, 없으면 송장 이력 첫 관측시각(`invoice_history[0].at`)
- 의미: 송장 넣고 하루 지났는데 마켓이 아직 배송중으로 안 넘어감 = 소싱처 품절·지연 대응 대상.
- **흐름 시작 경계 = 배송중부터**(사용자 결정). 발송처리/배송준비중 = 정체 후보.
- `market_check_error` 있는(확인 불가) 주문은 검사 대상에서 제외(거짓판정 금지).

## 10. 정합성·엣지 (CLAUDE.md 3대 원칙)
- 조회 실패·미매칭 → **"확인 불가"**, 있다/없다 단정 금지. 폴백 추정 금지.
- 마켓 실데이터 우선, 없을 때만 엑셀 폴백 — 폴백 시 근거에 "엑셀 기준(마켓 미확인)" 명시.
- 11번가는 규격 이슈·간헐 500 → 실계정 검증 전 "된다" 단정 금지. 미검증 마켓은 로그로 표면화.
- 마켓 API = 서버(AWS)에서만 동작([[project_market_api_server_side]]). 로컬은 목으로 테스트.

## 11. 테스트 (TDD)
- 매칭: 더망고 마켓주문번호 ↔ order_export 오픈마켓주문번호(마켓 슬러그 판별 포함).
- enrich: combined_order_rows 목 주입 → 필드 저장, 미매칭 "확인 불가", warnings 반환.
- ① 이중송장: 해외현지배송중 + 마켓 송장 있음 → 검출 / 마켓 송장 없음 → 제외.
- ② 정체: 송장+배송준비중+24h 경과 → 검출 / 배송중 → 제외 / 24h 미경과 → 제외 / 확인불가 → 제외.
- 24h 기준시각: shipped_at 우선, 없으면 invoice_history[0].at 폴백.
- 확인불가 주문은 어떤 검사에도 안 걸림.

## 12. 미결(구현/검증 단계 확정)
- `market_shipped_at`(발송처리일시)를 order_export가 마켓별로 실제 주는지 — 주면 사용, 없으면 폴백. 구현 시 실측.
- 11번가 매칭·상태·등록송장 실계정 왕복 검증(규격 이슈).
- 조회 기간 상한(엑셀 주문일 범위가 넓을 때) — 90일 상한 재활용.

# Phase 3 — 상품명 규칙을 한 번 만들면 여러 정책이 같이 쓴다

> 상위 설계서: `docs/superpowers/specs/2026-08-24-모음전-3계층-재설계-design.md` §4-2
> 사장님 요청 원문: 「상품명에 필요한 항목들 버튼으로 불러오고, 조립순서를
> 드래그앤드랍으로 변경할 수 있게 해줘」

---

## 1. 왜 이 단계가 필요했나

지금까지 상품명 조립 규칙은 **정책 안에** 있었다. 그래서

- 정책을 새로 만들 때마다 조립 순서·치환표를 **다시 채워야** 했고,
- 규칙을 고치면 그 규칙을 「복사해 간」 옛 정책들은 **옛 값 그대로** 남았다.

삼바는 규칙을 별도 저장소(`samba_name_rule`)에 두고 정책이 ID 로 **참조**한다.
그래서 한 번 채우면 그 규칙을 쓰는 정책 전부에 반영된다. 그 구조를 채택했다.

## 2. 🔴 시작할 때 발견한 것 — 칸은 있는데 읽는 곳이 0곳이었다

Phase 1 이 `NameRule` 표와 `market_policies.name_rule_id` 칸을 만들었지만
**읽는 코드가 한 곳도 없었다**(`grep` 실측: `shared/db.py` 의 컬럼 추가 목록 2줄뿐).

표만 생기고 배선이 없으면 화면에서 규칙을 골라도 나가는 상품명은 하나도 안 바뀐다.
같은 형태를 이 세션에서만 두 번 봤다 —
직전에는 **상품명 바이트 상한**이 같은 이유로 안 먹고 있었다(PR #1121 에서 고침).

## 3. 무엇을 만들었나

### 3-1. 배선 (`lemouton/policy/name_rules.py`)

| 무엇이 | 어디 것인가 |
|---|---|
| 조립 순서 · 치환표 · 마켓별 개별조합 · 길이 재는 법 | **규칙(0층)** |
| 글자수 상한 · 이음말 · 중복 단어 제거 등 나머지 | **정책** |

→ 규칙을 골라도 정책이 정한 나머지 값은 살아 있다. **부분 도입**이 된다.
→ 규칙을 안 고른 정책(`NULL`)은 지금까지와 **완전히 같다**.

전송이 실제로 쓰는 `to_payload.rules_for` 에서 얹는다 — 여기가 유일한 다리다.

### 3-2. 새 조립 조각

`브랜드` · `상품명` · **`품번`** · **`상품번호`** · **`카테고리`** · 직접입력

- **품번**은 원래 「담을 칸이 아예 없다」고 안내하고 있었는데, 칸은 `Model.article_no`
  에 있었고 **구성 사본이 안 실어 주고 있었을 뿐**이다. 사본에 실었다.
- **카테고리**는 맨 끝 분류만 쓴다 — `신발>스니커즈` 를 통째로 넣으면 상품명에 꺾쇠가 들어간다.
- 🔴 **색상·사이즈는 일부러 뺐다.** 옵션마다 다른 값이라 상품 하나의 이름에 넣으면
  어느 색을 골라도 틀린다(파랑·빨강이 섞인 상품에 「블랙」이 붙는다). Phase 4 에서 따로.

### 3-3. 화면 (정책 생성 → 상품명 탭)

- 규칙 세트 고르기 / 새로 만들기 / 저장
- 조각 **단추**로 넣기 · 칩을 **끌어서 순서 바꾸기** · ✕ 로 빼기
- **실시간 미리보기** — 6마켓 결과 + 글자수/바이트수 + 넘치면 「잘림」 배지
- 🔴 미리보기는 `/api/name-rules/preview` 를 부른다 = **전송과 같은 엔진**.
  화면에서 조립을 흉내 내면 「이렇게 나갑니다」와 실제가 갈린다.

## 4. 🔴 실화면 확인에서 잡은 것

**고른 규칙이 새로고침하면 풀렸다.** 저장은 돼 있는데 화면이 안 보여줬다.
원인 — 화면에 넘기는 `policy` 는 **정해진 칸만 담은 사본**이라 `name_rule_id` 가
아예 없었고, 템플릿에서 조용히 빈 값이 됐다. 사장님 눈에는 「저장이 안 된다」로 보인다.
시험 2건으로 잠갔다.
